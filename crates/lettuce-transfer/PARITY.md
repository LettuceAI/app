# lettuce-transfer: legacy parity notes

Facts about how `lettuce-transfer` relates to the legacy app (2.2.x): what each legacy import path preserves, where it deliberately differs, and how the backup format got here. The crate README describes the current design.

## Backup format

- The version 2 envelope corrects the legacy backup format's fast password hash, reused encryption nonce and unbound entry inventory.
- An earlier version 2 layout had a plaintext manifest that exposed section hashes and sizes, and media section names are image hashes; the manifest is now encrypted (backlog #17).
- The total backup limit was 512 MiB, which blocked large libraries; it is now 1 TiB (backlog #15). Legacy had no limit.
- New exports never write the legacy format. Version 1 imports convert into the current staged restore plan.
- The version 1 decoder keeps only its per-entry limit (`MAX_LEGACY_BACKUP_ENTRY_BYTES`, the largest non-zip64 entry). A version 1 entry is one AEAD message, so each entry is still limited to that size, and the decrypted documents held for planning have no total limit.
- Restore replaces the current data with a fresh database and keeps the previous database file (user decision 2026-09-14).
- Restore memory no longer grows with the media library: media is decrypted once per blob and installed from the verified staged copy.
- The live legacy database inventory used to reject large or unreferenced files and libraries over 512 MiB. The media plan now limits each referenced object only by the media store guard (2 GiB, the backup entry size), and the legacy media total is the backup total. The live inventory's source hash binds each file's size and content hash instead of its bytes.

## Legacy sources

- The importer reads legacy schema 92, which releases up to 2.2.5 kept: 93 and 94 only repaired group columns 2.2.0 already created, 95 rewrote group session override encodings (read in both forms), 96 reordered columns and renamed tables outside the schema. 2.2.0 stored 92 or 94, 2.2.1 stored 95, 2.2.2 to 2.2.5 stored 96.
- The legacy database and storage tree are read-only migration sources. A completed import keeps them until migration verification succeeds and the user explicitly approves deletion.

## Configuration

- Provider and model planning preserves stable legacy account and profile identities, protocol, endpoint and custom wire configuration, effective streaming and TLS state, model routing, modalities, supported generation parameters, prompt references and both legacy defaults. API keys and header values never enter the plan; it holds only pending secret kinds and header names. Unsupported provider and model configuration field names stay explicit deferred inputs whose values remain in the retained source.
- The legacy built-in llama.cpp credential becomes one deterministic synthetic account only when a llama.cpp model needs it; it carries no secret or endpoint.
- The version 1 configuration plan preserves the established provider routing order, model scope fallbacks, supported generation parameters, prompt content fallback and TTS provider defaults. Provider headers, inline or legacy-table API keys and audio API keys become scoped zeroizing secret values; machine-specific Kokoro asset roots never become canonical configuration.
- Provider `config` and `headers` and model `advanced_model_settings` that are not valid JSON or have the wrong shape fall back exactly like the SQLite import (empty config, no headers, empty settings), recorded as `legacy_value` skips; legacy restore wrote them back raw and its settings reader omitted them.
- Model scopes that are not a JSON array become text-only, non-string scope items are dropped and recorded, matching legacy restore normalization; JSON `null` counts as absent.
- A missing prompt type becomes direct chat like legacy restore's "undefined"; a non-string or unknown type also becomes direct chat and is recorded. `legacy_prompt_purpose` is the legacy prompt store's exact type table (camelCase names plus its snake_case lorebook aliases, no runtime text). Missing or null prompt entries are empty; a non-array value is empty and recorded (the content entry then applies); a valid array the new types cannot read still aborts.
- Content-only prompt templates become the single system entry the legacy runtime created. Undefined legacy templates are corrected to direct-chat documents because undefined is not an operational purpose. Model prompt references and deprecated system prompt text stay fingerprinted evidence and create no live model fields.
- Settings and model references legacy never cleaned up after a delete are cleared and recorded: the default provider and model, the summarization, group speaker, lorebook generator and help-me-reply models (legacy failed those features until another model was chosen, so clearing is a recorded correction), and the default prompt, every advanced prompt template id and a model's prompt template (legacy fell back to the default).
- `dynamicMemory` and `groupDynamicMemory` map every field the settings hold: `enabled`, the summary interval (0 becomes 1, as the legacy cycle used), run mode (unknown values run as `auto`, like legacy), decay, delete confidence, hard-delete ratio and recursive loops. `dynamicMemoryStructuredFallbackFormat` (`json`/`xml`) sets both direct and group settings; any other value is malformed.
- The summarizer and manager prompt template ids are retained as source ids (`dynamic_memory_prompt_source_ids`) and, like the lorebook generator prompt ids, checked against the backed-up templates but not yet materialized into settings on import. Version 2 graphs reject dynamic-memory prompt overrides that name a prompt outside the graph.
- `dynamicMemoryLlamaSamplerOverwriteEnabled` maps to the same-named setting (default true).
- `helpMeReply*` keys map to `help_me_reply`: a zero history count is a lossy notice, an unknown style is malformed, the model id and the two prompt template ids are retained and orphan-checked.
- Image feature keys map to `image_generation`: an unknown scene mode is malformed; avatar, scene and creation-helper model ids must name image-output models and the scene writer a model with text and image input and text output, else they are skipped as missing or incompatible. Only unknown keys remain unsupported notices.
- An app default, dynamic-memory, speaker, lorebook generator or help-me-reply model that is not a chat model, and a lorebook generator, dynamic-memory or help-me-reply prompt of another purpose, are cleared as `IncompatibleReference` (legacy loaded any template by id; the feature now uses its built-in document). Import admission accepts these skips; a stale feature reference used to fail admission.
- A configured `sceneGenerationModelId` that is missing or cannot output images is cleared and recorded, and scene generation is turned off: legacy generated no scenes with it, where the rewrite would otherwise fall back to the first image model.
- Scene image protocol (2026-09-23): legacy user prompt templates of the direct or companion purpose that copied `entry_scene_image_protocol` / `_local` get `lettuce_context::legacy_scene_protocol_conditions`, in both the backup and the database converter, so they keep legacy's id filter.
- The legacy app `settings.advanced_model_settings` goes through `legacy_model_parameters` into `LegacyBackupSettingsCandidate.model_settings` (replacing a former unsupported notice); the settings stage writes it as the global model settings, and version 2 backups carry it in `BackupGlobalSettings.model_settings`.
- Sprout: an Ollama credential's `sproutEnabled`/`sproutUrl`/`sproutApiKey` become its `ProviderConfig::Ollama` Sprout settings in both the database and backup paths, and the plain-text key becomes a `SproutApiKey` secret (pending source kind `provider_sprout_api_key`); a URL that is not http(s) is left out with a lossy notice. Provider backups list and rebind the Sprout secret with the account's other secrets.
- The legacy model pricing cache is parsed and validated but has no destination: the rewrite keeps no pricing cache and fetches prices when a cost is computed, so a non-empty cache is an `Unsupported` notice on `[]` and nothing is written. Entries keep their exact model key, original JSON and timestamp; known camelCase price fields must be finite non-negative USD values, unknown fields stay visible as notices. They lack the account, endpoint, revision and capture evidence an immutable cost basis needs, so they are historical only.

## Model settings mapper

- `legacy_model_parameters` (`legacy_backup_model_settings.rs`) is the single mapper for a legacy model's `advanced_model_settings`, shared by the backup planner and the live database preflight. Common sampling, reasoning, prompt caching, `forceSendThinkingState`, Ollama and OpenRouter keys go to `ChatParameterProfile`; every `llama*` key to `LlamaCppSettings` (sampler keys to `LlamaSamplerSettings`); every `sd*` and `sdcpp*` key to `StableDiffusionSettings`; each of the nine `featureGenerationSettings` slots to its `FeatureGenerationParameters` (present fields `Set`, absent ones inherit, matching legacy `feature_model_overrides`).
- A value of the wrong type or outside the legacy editor's range is left out with a lossy notice instead of aborting (legacy accepted `ollamaRepeatPenalty: 0`, which the new profile rejects). Keys legacy never defined get an unsupported notice, nulls are ignored, and the backend-owned `llamaLastRuntimeReport` is dropped with a lossy notice.
- Legacy llama sampler orders import as the old runtime read them: names trimmed and lowercased, aliases accepted (`topk`, `typ_p`, `temperature`, `adaptive` and others), unknown entries skipped, repeats dropped. Before, one unknown entry dropped the whole order, which lost every order saved by 2.2.5 (whose default includes `adaptive_p`). `llamaAdaptiveTarget`, `llamaAdaptiveDecay` (also in feature slots) and `forceGemma4Reasoning` map to typed settings.
- Direct sessions carry `generation_settings.model_settings`: the session's `advanced_model_settings` through the same mapper when it is an object, otherwise the flat temperature, top-p, max output tokens, penalty and top-k columns (legacy `build_session_advanced_model_settings`). Legacy read fewer fields from a session and from the app layer than from a model: prompt caching and the OpenRouter pin only from the model, image generation settings and feature slots never, and the app layer never the thinking state, top-k, frequency and presence penalties or reasoning; `legacy_settings_layer` leaves those out with lossy notices. A session's prompt cache TTL only filled in for a model whose caching was on without a TTL; imported model caching always carries its retention, so the session TTL is dropped. The thinking state was model-first in legacy, which request resolution must keep. Group conversations reject a model settings layer (legacy group sessions had none).

## Authored profiles

- The persona plan preserves legacy identity, authored text, crop, LoRA recommendation, lorebook references, timestamps and the single default owner. Avatar and design images stay typed unresolved locators until media import.
- The lorebook plan preserves root detection policy, the unresolved avatar and every persisted entry field in deterministic order.
- The authored conversion preserves the default persona, every authored text and provenance field, legacy presentation and companion payloads, ordered rules, scenes and variants, starters, LoRA recommendations, timestamps and unresolved media locators. Character and persona lorebook order stays explicit; the optional compatibility binding document keeps disabled rows instead of repeating the legacy importer's silent drop.
- Persona and lorebook values legacy read leniently follow the SQLite import exactly and are recorded: persona design reference or lorebook id lists that are not string arrays become empty, non-UUID, missing or repeated persona lorebook ids are pruned by `reconcile_legacy_persona_lorebooks`, unknown detection or match modes become recent message window or literal, malformed keywords become empty and regex keywords legacy's matcher could never compile are pruned by `reconcile_legacy_lorebook_keywords`. Non-string JSON values in these string fields still abort.
- Character and starter references legacy never cleaned up are cleared or pruned and recorded: a character's default scene, default model (legacy failed with "model not found"; clearing is a recorded correction), default starter and missing or non-UUID active lorebook ids (repeats dropped; legacy injected them twice in direct chats), a scene's selected variant (legacy fell back to the scene content), a starter's scene and override lorebook ids. Character and starter lorebook links are pruned the same way whether or not the lorebooks document exists. A character's deleted direct or group prompt and a starter's deleted prompt are kept and recorded, because legacy treated them as explicit choices and fell back to the app template. A JSON `null` override means no override silently; malformed override JSON means no override, recorded, like the legacy session reader. A starter whose character is missing still aborts because legacy's foreign key cascade made that impossible.
- A character direct, group, companion or starter prompt, or a group profile prompt, whose purpose differs from the one the launch planner looks up, and a character default model or group member override that is not a chat model, are cleared as `IncompatibleReference`. A missing prompt stays referenced and resolves to the app default like legacy.
- Character lorebook rows follow the legacy restore rule: only enabled `character_lorebooks` rows count, they replace the character's list only when the character has one, and rows naming a deleted character or lorebook are recorded instead of aborting.
- A design reference that repeats the background or another reference is dropped and recorded, since one image cannot fill two character media slots.
- Companion JSON becomes a `CompanionSoulConfig`: keys the rewrite has no field for (`memory`, `timeAwareness`, `context`, stray nested keys) are dropped and recorded; missing affect, regulation and relationship values take legacy defaults; authored facts follow legacy storage normalization (default policy by category, slot from category, `authored` kind, deterministic ids for blank ids); facts with an unknown category, blank value or invalid validity are dropped and recorded; `prompting.promptTemplateId` is kept as a prompt source id; a companion value on a roleplay character is recorded and dropped.
- Voice: a `voice_config` user voice resolves to the imported `VoiceProfileId`, a missing one records `VoiceReference`/`MissingUserVoice`; a provider voice is kept verbatim as an unresolved legacy locator.
- Chat appearance becomes the complete appearance legacy displayed: defaults, then the legacy global `advancedSettings.chatAppearance`, then the sparse override. Keys apply one at a time with dependency retries; a key that cannot be represented keeps the inherited value and is recorded. Widget nodes convert camelCase keys and `12h`/`24h`; library and upload images become unresolved legacy tokens.
- Reusable groups keep ordered and muted members, an explicit persona or none (a group whose `persona_id` is NULL used no persona and never the default, `group_chat_manager/mod.rs` 5866-5870, so it maps to `Selection::Disabled`), archived state, chat and memory modes, all five speaker policies, per-member model overrides, group prompt selections, lorebook order and policy, raw appearance, starting-scene variants and both unresolved background locators. Director and Director Action need no persisted selected speaker; the legacy UI supplied it per send or continuation.
- Group references legacy never cleaned up are pruned and recorded: members whose character is gone (legacy speaker selection skipped them), muted ids and model overrides for non-members, overrides whose model is gone (legacy fell back), a deleted persona (legacy's foreign key set it to null), stale group lorebook ids, and a starting scene's missing selected variant (legacy group prompts used only the scene content). Stale group prompt ids are kept and recorded because sessions copied them as explicit choices.
- A group with fewer than two members or with every member muted, before or after pruning, is skipped and recorded (`group_profile`/`undersized_group`, user decision 2026-09-13).
- A group session saved before sessions linked a reusable group gets the group legacy's v42 migration created for it: a group under the session id built from the session's cast, mode, scene, background, lorebooks and prompts, which the session then links to. A session linking a deleted group is recorded as `GroupReference`/`MissingGroup`.

## Media

- The composed media plan deduplicates persona avatar, design reference and lorebook avatar uses by relative legacy file, with size and BLAKE3 evidence. Missing, unsafe, ambiguous and oversized sources are typed failures.
- Version 1 authored locators resolve directly against the retained archive bytes: persona and character avatars use their exact owner directories; lorebook icons, design references and character, group and scene backgrounds use legacy's image-reference convention. Shared objects are hashed once and keep every typed owner and ordinal use. A reference whose file is absent is cleared and recorded as `MissingMediaFile`, like the legacy SQLite import (persona avatar with its crop, design references, lorebook avatars, and `CharacterMedia`/`GroupMedia` slots keyed `<id>:avatar|background|design:<locator>|scene:<scene id>`). Ambiguous, unsafe or oversized references still reject the media plan; the number of references is not limited.
- Legacy chat attachments (2026-09-22; previously dropped): every persisted attachment of direct messages, group messages and group variants (`sessions/<owner>/<session>/<file>`) is planned as a `MessageAttachment` use, one per file however many rows repeat it. Bytes are sniffed at planning: images become `message_image`, audio `message_audio`; the legacy file name (a generated image's prompt) becomes the source label, cut to 256 characters without control characters. Missing, unsafe, oversized or unsupported files (legacy's raw `.webp` fallbacks, AAC and AIFF audio) and inline-only data are recorded, never fatal. Conversation import appends them as `MediaAsset` parts after the text; the rendered variant also gets the message's attachments, deduplicated by id; media on non-rendered revisions and candidates is historical.
- Legacy `data:` images and session backgrounds (2026-09-22; previously fatal or dropped): legacy stored group and group-session backgrounds, and sometimes other images, as `data:image/...;base64,` URLs. Each is decoded into in-memory `inline/<blake3 of the URL text>` media before planning; other URLs legacy displayed as-is (`http(s)`, `blob:`, `asset:`, `tauri:`) and undecodable or non-image data are missing media and recorded, where they used to abort the import as unsafe.
- A session's own background is planned as a `ConversationBackground` use: a direct session's `background_image_path`, a group session's `config_overrides.backgroundImagePath` (legacy resolved every other group session value from its group, which the conversation now follows live). Conversation import sets the image, or `Hidden` when the value was empty or its image could not be imported, as legacy then showed none.

## Conversations

- Direct sessions keep each root and derived session, archived state, character, persona, scene and prompt selections, author and generation overrides, voice policy, raw companion and dynamic-memory documents, and every message and variant in archive order. Message visibility, parent links, selected variants, usage metrics, MTP statistics, reasoning, memory and lorebook references, attachments and effective timestamps stay explicit.
- Branch links are repaired rather than validated: legacy deleted a session row without touching its branches, and "Branch to character" linked a session to another character's root. A parent or root that is missing, belongs to another character or group, or closes a loop is cleared, a branch message missing from the session is cleared, the root becomes the topmost surviving ancestor, and each change is a `session_link` skip. The same repair runs for group sessions.
- Equal message timestamps and unordered legacy variant queries are reported as ordering loss; archive array order stays as an ordinal.
- Direct session references legacy never cleaned up are cleared and recorded: deleted override lorebooks (legacy found nothing), a scene the character no longer has (legacy used an empty scene), a message's deleted model (only the debug view read it) and a missing selected variant (falls back to the last variant like the legacy chat view). A missing character or persona still aborts because legacy's foreign keys made those impossible.
- Group sessions add the frozen member and mute order, the optional reusable group link, the persona (a `config_overrides` `personaId` of null, empty or a deleted persona is the explicit no persona, `persona_disabled`), chat, memory and speaker policies, per-member model overrides, prompt selections, starting scene, branch topology, participation state and the full history. Speaker attribution, selection reasoning, Gemini content, usage JSON, attachments and dynamic-memory documents stay exact.
- Legacy's send path selected explicit mentions and its continue path accepted an explicit member per request, including muted members, while automatic selection excluded muted members. Session snapshots may therefore keep an all-muted cast even though new reusable groups need an active member.
- A missing reusable group link is cleared and recorded, like legacy's foreign key set it to null. A deleted session prompt is kept and recorded: legacy treated it as an explicit choice and went straight to the app group template, so the materializer resolves a missing explicit prompt to the app default rather than inheriting.
- Group references legacy never cleaned up are cleared and recorded: deleted lorebooks, model overrides for non-members or deleted models (legacy fell back to the character's model), deleted message and variant models, a missing selected variant (falls back to the last variant like the legacy group chat view) and a starting scene snapshot's missing selected variant (legacy used only the scene content).
- Members and message speakers whose character was deleted are kept and recorded as missing characters: the user decided that a deleted character stays in a group chat as an ignored "Unknown" participant, and legacy likewise kept those messages and skipped the id during speaker selection. Participation rows and speakers for a character removed from the session (legacy removal left both behind) are kept the same way; the conversation writer gives such a speaker its own ignored participant, because only members become participants.
- A linked group session reads each value from its `config_overrides`, else from the group row (2.2.1 repair encodings included). A starting scene other than the group's becomes `starting_scene_override`, its background dropped as lossy since legacy group chats never showed a scene background; an unmappable scene is lossy and follows the group. A model override for a member the group row does not list is lossy; session model ids go through the group's canonical model id mapping; `lorebooks_overridden` says whether the session chose its own lorebooks.
- Finite historical API costs stay exact even when legacy pricing produced a negative value; no current pricing formula runs.
- Legacy rows have no generation attempts, protected snapshots or selected branch head, so none are fabricated.

## Other legacy documents

- ASR learning: the plan keeps vocabulary, correction, ignored-suggestion and voice-example rows in stable legacy id order with exact authored and normalized text, counters, confidence, timestamps, language, scope and links; voice audio paths stay unresolved media evidence; malformed or orphaned rows reject the whole plan. Admission assigns stable ids to every row, voice audio joins the media plan with its original locator as evidence and a safe import key, and ASR materialization resolves every row and link, requires the audio completions and returns one aggregate receipt.
- The version 1 ASR backup document maps into the same plan, assigning deterministic plan-local ids from archive order because the legacy exporter omitted database ids. Duplicate semantic rows or invalid normalization, metrics, flags or timestamps reject. The legacy full backup never exported voice examples, their audio or learning relationships, so the plan reports that absence.
- The legacy version 2 ASR JSON's nullable ids, counters, timestamps and native audio locators are parsed without making that format part of the speech domain.
- Usage history keeps request, session, character, model and provider labels, operation, finish reason, every token counter, success or error state, the three stored money totals and all metadata. Known counters and costs are validated from their strings without running a pricing formula. The rows predate turn, attempt, job and dispatch identities, so they are historical only and never enter the current ledger as new charges. Duplicate ids or metadata keys, negative counters, invalid timestamps and non-finite costs reject.
- Scheduled notes keep archive order, identity, companion owner, label and content bytes, availability, end-exclusive expiry, recurrence window, enabled state and timestamps. Duplicate ids, missing or non-companion owners, unknown recurrence values, negative times, expiry at or before availability and reversed write timestamps reject. Text is not normalized and schedules are not evaluated during conversion.
- Companion shared memory keeps each companion's manual memory array, embedded dynamic-memory projection document, summary and token count, tool-event history, progress and error state, raw Soul growth, persona-keyed relationships, continuity episodes and timestamps. Fully specified Soul facts can seed one initial Soul snapshot; relationship values seed initial conversation snapshots only for matching continuity episodes; manual memories, embedded projections and tool events stay evidence because the legacy document cannot supply memory-space revisions, access receipts or execution history. The old importer's table-wide deletes and silent Soul normalization are not reproduced.
- Soul growth from backups, legacy databases and character files is repaired the way legacy normalized it before storing (blank id, policy and slot filled, confidence and weight clamped to 0..1, zero evidence count taken from sources, zero creation and validity times set to the state's time); only a fact that still cannot be represented is dropped and recorded. One bad fact used to drop the whole Soul growth.
- The standalone memory embedding document keeps owner order, owner kind (direct, group, companion-shared), exact canonical JSON and every vector, score, counter, timestamp, category, temporal attribution, supersession field and entity anchor. Each owner must resolve to a planned conversation or companion, and its canonical JSON must match the exporter's embedded copy byte for byte. Duplicates, orphaned supersession links, unsupported or mismatched dimensions, non-finite or out-of-range scores and invalid timestamps reject; equal creation timestamps are reported. A compatible item with a supported vector can seed a memory item and projection; one without a usable vector needs a rebuild; other records stay evidence. The legacy importer's table-wide delete and malformed-JSON-to-empty behavior are not reproduced.
- Creation-helper sessions keep the exporter's recency order, goal and status, byte-exact nested session and upload JSON, drafts and history, chat messages, tool calls and results, block order, target and timestamps. Outer and nested values must agree, edit targets resolve through the authored graph, draft scene links are closed, and cached image asset ids resolve to retained archive images; older inline base64 and newer asset-backed uploads are both kept and hashed. A pristine active create session whose draft fits the target can serve as initial draft input only; no legacy row becomes a durable workflow record, since it has no revision, proposal identity, turn or attempt identities. The old importer's table-wide delete is not reproduced.
- `image_loras` (2026-09-22) is read only from the live database (archives never carried it) as the `ImageLoras` document, planned as `plan.images` and sealed by its content hash (re-derived by `verify_seal`). Paths stay relative to the LoRA root; keywords are normalized like legacy read them (trimmed, case-insensitive unique, at most 32); a sha256 that is not 64 hex characters, unknown sources, negative sizes and unparseable keyword JSON are replaced and recorded. The `images` stage keeps whichever row of a path changed last.
- Playground history (2026-09-22, `playground_generations`, live database only) is planned as `plan.images.playground` and written into `playground_history` and `playground_history_images` as `origin = imported` entries (ids derived from the source id, `params_json` and status kept verbatim, old asset ids kept as `source_asset_id`). Each image file (`images/<assetId>.<ext>`) is a `PlaygroundImage` generated-image asset; missing, ambiguous or unusable files and lossy `images_json` entries are recorded and the image keeps a null asset.
- `llm_generation_metrics` (2026-09-24) is read only from the live database as the `LlmGenerationMetrics` document, planned as `plan.llm_metrics` and sealed by its content hash. Installs without the table import no metrics, and installs from before the `message_id` column no message links. Each row keeps its id, `created_at`, `model_name` (as the model path) and legacy message id; a summary that is not a JSON object becomes `{}` and samples that are not an array `[]` (as legacy read them back), recorded, as are rows without a usable id or integer timestamp. Only the newest 500 by `created_at` are kept, as both apps retain; dropping older rows is a lossy notice. The `llm_metrics` stage receives each row with its imported message id (`LegacyIdScope::source` of the legacy message id).

## File formats

- Character cards follow the old app's structs, field order, trimming, definition layout (`[Personality]`, `[Scenario]`, `<example_dialogue>`; system prompt and post-history instructions dropped on import) and detection order. PNG chunk CRCs are not checked. `export_definition` strips old prompt sections and falls back to the description; a database export passes no embedded lorebook, a conversion may. Scene ids and materialization belong to the import use case.
- Entity packages use `unified-entity-card` 0.2.0 like the old app and the old app's export package serde layout; UEC v2 writing merges other scenes into the picked scene's variants and writes `_ID:` prompt templates and asset locators. Error texts match the old app's. Correction: a v2 import keeps nickname, creator, creator notes (and multilingual), source and the embedded lorebook, and a persona keeps its nickname; the old app lost them in the downgrade. The workspace `serde_json` has `float_roundtrip`, so a rare float may print a different last digit than the old app on re-export.
- Character file import scheduled notes follow legacy (trim, empty content skipped, times clamped at 0, recurrence normalized, missing created or updated times become now) and are kept only for companion characters. Corrections: legacy's insert misaligned a placeholder and always dropped `default_model_id` (now kept when the model exists); legacy overwrote `source` with `["lettuceai"]` (the file's source is kept); legacy stored scene background strings raw (data URLs become assets, other strings are dropped); bundled lorebook entries keep their packaged match mode (legacy forced literal, so a regex entry stopped matching after a round trip). `lorebook_details_from_candidate` is shared with the legacy import writer.
- A character file's companion shared memory becomes `CharacterFileCompanionMemory`: memory texts (trimmed; blank or oversized ones recorded) become a pool of memories the companion's chats share, Soul growth becomes the character's Soul facts when they parse exactly, relationship states become rows for the default persona and for personas that exist here (others recorded); the summary is lossy because a pool summary belongs to a chat, and tool events and run status are not carried.
- Character export writes the old app's package: definition stripped of legacy card prompt sections or else the description, active scenes and variants in order, starters as chat templates, enabled bound lorebooks in binding order, scheduled notes, mode and memory type always present, companion config in the legacy `CompanionConfig` shape with `memory.sharedAcrossSessions` and `timeAwareness`, user voices as `{source: "user", userVoiceId}`, provider voices as their stored legacy JSON. V1 and legacy JSON export are refused with legacy's texts. Differences: scene backgrounds are exported as data URLs instead of local image ids, crops are written in their shortest decimal form, an archived default scene is left out, empty source and tag lists are omitted, lorebook avatars are not exported, and the deprecated character system prompt is never exported. A companion's shared memory is exported from its pool (active memories only), Soul facts and relationship states, without a summary or tool events.
- World Info follows the old app's layout: entries keyed "1", "2", ... in lexical order; import uses `keys`, else `key`, ignores secondary keys, skips empty content, orders by `insertion_order`, then `displayIndex - 1`, then the map key - 1, and matches literally. USC 1.0 lorebook cards carry no lorebook id or match mode per entry; the old app had no USC lorebook reader.
- Chat JSONL follows the old app: a compact header (`user_name`, `character_name`, `create_date`, `chat_metadata`, `{group: true}` for groups), one compact line per message with blank content left out (`send_date` in UTC RFC 3339 with milliseconds, `swipes`/`swipe_id` for alternatives; direct chats mark the selected variant, else the shown content, else prepend it; groups show the selected or first variant). Reading detects the header, takes `mes|content|text|message`, times from `send_date|createdAt|timestamp|time` (seconds below 1e10), and treats more than one named assistant speaker as a group chat.
- Prompt files: USC cards use legacy field order, empty `content`, and entries in the legacy `SystemPromptEntry` shape. SillyTavern presets rewrite `{{scenario}}`/`{{personality}}` to `{{scene}}`/`{{char.desc}}`, use legacy position codes, the eight SillyTavern markers, one prompt order with character id 100001, and the preset-level texts legacy wrote; the JSON is written with sorted keys (legacy kept insertion order). Reading follows the old import page: a USC card needs a non-blank name and a known prompt type (else it becomes a direct chat prompt, as `undefined` could not run; legacy's page accepted only 17 types, the rest are kept so this app's own cards round-trip), entries without content are dropped, depths clamp at 0 and message and turn counts at 1, image slots keep the five legacy slots, scene image protocol entries get their gate from their legacy id, an interval entry without a turn count (legacy never fired it) is kept disabled, and content without entries becomes one system entry. A preset takes the prompt order block matching the most identifiers (then the longest), skips markers and blank prompts, lets the order's `enabled` win, marks nothing as a system prompt, drops conditions and the chat background slot, and is named after the file.
- Chat template files accept a USC card, the legacy `{version: 1, kind: "chat_template", template}` JSON or a bare template object with a non-blank name, and keep user and assistant messages with string content.
- Model files: rewrite-only values (split KV types, cleared feature overrides, feature-level context, reasoning, caching and Ollama resource overrides) have no legacy key and are not written; a pinned OpenRouter provider is written with its id as its name, which legacy required. A reasoning budget under 1024 or a repeat penalty over 2.0, which the domain allows but legacy's editor did not, is written and reads back as lossy. A file's `llamaLastRuntimeReport` is ignored like legacy's upsert ignored it. The 2.2.5 DFlash keys (`llamaDflashEnabled`, `llamaDflashDraftTokens` 1-15, `llamaDflashMinProbability` 0-1, `llamaDflashModelPath`) read and write like the MTP ones. Reading takes a USC card or a model object: name and provider id required and trimmed, label and display name default to them, scopes keep text, image and audio in that order (text when none), and advanced settings are taken when they are an object. Legacy's model prompt template and deprecated system prompt are not carried.

## Memory backup

- `MemoryBackup.unbound_pools` carries companion pool spaces no conversation is bound to (a pool from a character file before its first chat, or one whose chats were all deleted); they restore before conversations with their items and projections. Such a pool used to make the whole backup fail.
