# lettuce-app

The composition root and the application layer. Every workflow that spans more than one domain lives here: launching and running a chat turn, the background memory, companion and lorebook jobs, image and speech work, model installs, file import and export, legacy import, backup and restore, sync sessions and hard delete. `AppBackend` is the single entry point a host (the Tauri shell, or a test) calls.

The crate may depend on every other crate, and nothing depends on it. It holds no business rules of its own that a domain crate could hold: it resolves inputs, reads through repository ports, calls the pure domain functions, dispatches providers and commits through the repositories. Durable state lives in `lettuce-database`; provider I/O in `lettuce-providers`, `lettuce-local-llm`, `lettuce-image-generation` and `lettuce-speech`; job lifecycle in `lettuce-jobs`.

The crate never depends on Tauri; `api/` is the surface the Tauri shell (`apps/tauri`) wraps.

What stays with the host: the Tauri commands and events, window and platform integration, the native `SecretStore`, the TLS policy, filesystem roots and the `FileAccess` implementation. `api::startup` starts the worker threads. Every repository call is synchronous SQLite work, so it runs on a blocking worker or a worker thread, never on the UI thread or an async runtime thread. The application never substitutes an in-memory secret store in production.

## Application API (`api/`)

`api/` is the application API the frontend reaches through the Tauri shell. Every call is a plain async function, `async fn x(context: &ApiContext, request: XRequest) -> Result<XResponse, ApiError>`, over `lettuce-contracts` DTOs, with no Tauri type anywhere, so the whole surface is tested without a webview. The shell's commands are one-line wrappers around these functions.

`ApiContext` is cheap to clone and holds the `AppBackend`, the host's `SecretStore`, the inference port, the loader of the optional embedding and emotion models with the slots holding them once loaded, the optional media store, the `ApiEventSink`, the clock, the host's `FileAccess`, the app data and resource folders, the database files used for media collection, the per-turn stream sinks, the job state (watch streams, running jobs' cancellation tokens, install work) and the workers' wake-ups. `ApiContext::new(ApiContextParts)` builds it from explicit parts (tests use an in-memory backend and a fake provider); `ApiContext::open_desktop(app_data_dir, resource_dir, secret_store, events, files, asset_url_base)` opens production: the `DirectorySnapshot` and `FilesystemAuthority` over the app data directory, the active database through `AppDatabaseLocation`, the media store over the `MediaBlobs` root and the remote `ProviderRuntime` over the native secret store and the device TLS policy. The host calls `startup` once (see Startup and shutdown) and stops the workers it returns on exit; `begin_shutdown` cancels the context's shutdown token, which every job a worker runs is linked to.

Every repository call runs on the blocking pool (`ApiContext::blocking`, a `spawn_blocking`), never on an async runtime thread.

Errors: `api/error.rs` is the one place a domain or runtime error becomes an `ApiError`. `IntoApiError` maps conversation, character, launch, companion send, job store, dispatch, cancellation, worker and media errors to a stable `ApiErrorCode`; a validation error names its field in `ApiErrorDetails::InvalidField`, and an id that is not a UUID names the request field. The message is the error's English text, for logs only; the frontend localizes by code.

Events: `ApiEventSink` receives application-wide `ApiEvent`s (the shell broadcasts them): `GenerationSettled` whenever a turn reaches a terminal state, `JobUpdated` for every job change (see Jobs), `ConversationChanged` and `ConversationRemoved` from the conversation change feed (see Conversations), and `RequiredModelsChanged` whenever `models_changed` runs, so open chats re-read the models they miss. Token streaming does not use it: `conversation_send` takes a `GenerationEventSink` (the shell passes the command's channel), attached to the turn until it settles.

Media: contracts carry `AssetRef`s (the asset id and its `url`, the host's asset URL base joined with the id), never bytes, so the UI never builds a media URL. `read_asset` reads the requested `AssetRange` of a ready asset (whole, `start..=end`, from `start` capped at `OPEN_RANGE_CHUNK`, or the last `n` bytes) by seeking the blob, so only those bytes are held in memory, and reports a range past the end as unsatisfiable; no API call takes or returns image bytes or base64, and media a call accepts arrives as a `FileSource` the backend reads, validates and ingests itself.

Conversations (`api/conversations.rs`):

- `conversations_list` pages conversations, most recently updated first, from the `ConversationOverviewReader` read model. The request filters by lifecycle (`active` by default, `archived` or `all`; tombstoned ones never appear), kind, character (one-to-one chats with it) and source group (chats launched from it). A row carries kind, title, each character participant's avatar, the newest visible non-system message's text on the selected branch cut to 400 characters as the preview, whether it is archived, its source (character or group), the count of visible non-system messages on the selected branch, a group chat's live chat mode (the conversation's own, else the group's current, else the launch value, as a turn reads it) and the optional models it misses.
- `conversations_latest_by_character` and `conversations_latest_by_group` page, for every character or group with a chat, its newest chat (archived included), newest first. The chats screen shows a character unless its newest chat is archived; the groups screen opens a group's newest chat.
- `conversation_open` returns the header (participants with their character avatars), the active branch and its head, the newest message page, the pending turn, `can_send` (not tombstoned, which a sync can leave behind, no unsettled turn and a user participant; an archived chat stays usable), the conversation revision and its own settings revision, whether it is archived, its source, a group's chat mode and the models it misses. `conversation_messages` pages older messages with the timeline cursor. A page holds only visible messages, oldest first: hidden ones (legacy system notes that were never shown in chat) and tombstoned ones are left out, so a message carries no visibility; each shows its active revision or selected candidate as text and media parts plus its reasoning summary and pin state, and a generated reply carries its candidate ordinal and the message's candidate count.
- `conversation_send` builds a `SendConversation` on the active branch whose operation key is the request's `client_operation_id` and whose digest covers the conversation and the text, so a retried send replays the first one. It always goes through `CompanionTurnCoordinator`, which commits a direct companion send with its state transition and any other send as a plain send. A key already used with different text is `Conflict`, checked against the operation record before anything else, so it holds while a turn is live; any other conflict while the conversation still has an unsettled turn is `Busy`. The turn gets the caller's sink and is scheduled with `ConversationGenerationDispatchCoordinator::schedule`; the call returns the user message and turn ids at once and wakes the worker. A replayed send whose turn already settled returns the same ids without scheduling and sends that turn's last event to the new sink. If scheduling fails after the send committed, the turn is settled (`settle_unrunnable_turn`; a turn that had not started is cancelled), the sink gets the turn's last event and `GenerationSettled` is emitted before the error returns, so the conversation accepts the next send.
- Turn operations (`api/turns.rs`) share one preflight before they write: the conversation exists and is not deleted (`NotFound`), the models the operation uses are installed (`ModelRequired` or `ModelUnavailable`), no turn is live (`Busy`), and the memory rewinds a delete owes the chat are finished (`DynamicMemoryDeleteAfterCoordinator::complete_pending`); a rewind that still fails refuses the request as `Unavailable` with `PendingMemoryRewind`, so nothing generates on top of memory that is ahead of the chat. `conversation_send` runs the same preflight. A repeated request replays without it: the same key and request returns the first turn, and a settled turn sends its last event at once; another request under the key is `Conflict`. After the preflight a group chat gets a row for every member it gained (`ensure_group_members`), and a request whose `expected_revision` is not the revision the caller last saw is `Conflict` before that write; the revision after the write is the one the turn begins from. `conversation_regenerate` trims `guidance` and `model_profile_id` (blank is none), resolves a model into a conversation snapshot, and needs an assistant reply of the selected branch that was not deleted (`NotFound` otherwise, `InvalidInput` naming `message_id` for a message that is not a reply); a one-to-one chat regenerates only its newest message, a group chat any reply, by its speaker or by `forced_speaker_participant_id`, which must be an effective member (`InvalidInput`). A reply owned by a parent branch is `Unsupported` from a child branch and regenerates from the branch that owns it, adding a variant every branch showing the message sees. The turn regenerates the variant the reply shows, or the one an edit superseded. `conversation_continue` adds a new reply after the branch head (an empty branch is `InvalidInput`), through `CompanionTurnCoordinator::begin_continue`, which never classifies. `conversation_retry` takes only the conversation and the failed or cancelled turn (`Conflict` for another state, `NotFound` for a turn of another conversation or branch) and reads both revisions itself. `conversation_add_user_message` trims the text (blank is `InvalidInput`), appends a user message to the selected branch without a turn and returns the message. All four restore an archived chat to Active in the same transaction.
- Inspection reads (`api/inspect.rs`), none gated to development mode. `message_prompt_snapshot` returns the request a reply was generated from, read from the initial dispatch record of the attempt that produced the variant the message shows (or the variant an edit of it superseded): the provider-neutral messages, the model's name and provider kind, the resolved sampling parameters, the budget report and, when the request was recorded with them, a per-section breakdown; the account, endpoint and credentials never leave the record. The context assembler records the sections while it assembles (`ContextAttributions::sections`): the character and persona with their names, the scene, each activated lorebook entry by title, the memories, the author note, the companion state and scheduled notes, the group cast and each rendered prompt entry by name, each with its tokens estimated from the final placed content (bytes over four, cumulative rounding); history, media and tool sections complete the breakdown, whose sum equals the budget report. Because they are stored with the request, they show what was sent even after the character, persona or lorebooks changed; a request recorded before sections existed has `sections: None` and `sections_unavailable: PredatesBreakdown`, never a reconstruction from current state, and a reply with no recorded request (an imported one) is `NotFound`. `conversation_speaker_selection_preview` renders the prompt the next LLM speaker selection would send through the same private builder as the turn (`PreparedConversationGenerationJobRunner::speaker_selection_preview`), from the live cast and the selected branch and, for a user message not sent yet, with it appended; no provider is called, a one-to-one chat is `Unsupported` and a group without a member that can speak `Conflict`. `conversation_participation_stats` lists each character participant with the visible replies it spoke on the selected branch, the rounded share of all of them and its newest reply's message and time, counted from the timeline on every call. `message_companion_effect` reads the effect of a reply (its status, summary, relationship and emotion movement, signal changes and memory changes), or none.
- `conversation_help_me_reply` (`api/jobs/text.rs`) queues the reply helper as a `CreationRun` job and returns it. Its request key names the job through the job operation record (the same key and request returns the same job, another request under the key is `Conflict`), and what it works on (conversation, the draft when the mode is `enrich` and the draft is not blank, swap places) is recorded in generic `job_details`; `job_operations` stores its canonical request receipt in the same admission transaction. A disabled feature is `Unsupported` before a job exists. `TextFeatureHandler` (in `JobHandlers::standard`) runs the queued jobs that have such a detail, each in its own lane: it registers the model stream under the request id and forwards every delta to the job's watches as `JobEvent::TextDelta` (a watch that attaches after the model started first receives the text streamed so far, kept per running job and dropped when it ends), runs `ReplyHelperCoordinator::generate` under the runner's cancellation token so `job_cancel` reaches the provider, and stores the cleaned text through a `ResultRecorder` before the job settles, so the settled job's `result` is `GeneratedText`. A cancelled job ends `Cancelled` with no text stored; a run that produced no text fails with `JobFailureReason::HelpMeReplyNoReply`, a chat without visible messages with `HelpMeReplyNoHistory`, a missing or unreadable model with `HelpMeReplyNoModel`, taken from the label the job's error carries (`jobs/failure_labels.rs`). The history is the last `history_count` visible messages of every role on the selected branch, and a group's cast is its enabled members.
- The message signal feed: the database writes `message_signals` (one row per kind and message, moved to a new position each time) from a trigger when a companion turn effect leaves `processing`, and the conversation change feed publishes each new signal beside the conversation changes, coalesced the same way: `ApiEvent::MessageEffectSettled { conversation_id, message_id }` replaces the poll the effect view ran while an effect was processing (`ApiEvent::MessageSceneImageChanged` has its own signal kind). It reads only after the database signalled a committed change.
- `generation_cancel` cancels the turn's latest job with reason `User`. A queued job is settled on the spot (the sink gets `Cancelled` and `GenerationSettled` is emitted); a running one is signalled and settled by the worker; a settled one is left alone. A turn that is unknown, has no job or already settled is a successful no-op. A stopped reply that already streamed text keeps it as the reply, in one-to-one and group chats alike.
- `conversation_launch_direct` launches a one-to-one chat with a character through `launch_direct_conversation`, titled with the request's trimmed title or, when it is blank or absent, the character's name, with the chosen scene or the character's default one, the chosen chat template if any, the default persona and the user participant named `User` (the name the importers use). A scene or template that is not the character's is `InvalidInput` naming `scene_id` or `starter_id`. The request's key is the launch operation key, so a retry of the same request (including `AlreadyLaunched`) returns the same conversation, and the same key with another request (another kind, character or group, title, scene or template) is `Conflict`. The planner stores a digest of the request's own fields with the conversation, so it can tell the two apart even when the request no longer prepares (a source archived since, or a scene of another character).
- `conversation_launch_group` launches a chat from a group profile through `launch_group_conversation`, titled with the group's name, idempotent by its key the same way.
- The conversation change feed (`api/conversation_feed.rs`) follows `ConversationChangeFeed::conversation_changes_since`, the database's record of the latest committed write of each conversation. Like the job feed it never polls: the database raises `on_conversation_change` after each committed transaction that changed or removed a conversation, the feed waits 250 ms to gather further changes and publishes each changed conversation once as `ConversationChanged`, or `ConversationRemoved` when a purge removed it, so one conversation sends at most four events a second and a rolled-back write sends none. A read that fails is retried without waiting for another signal, after a delay that doubles from 250 ms to 30 s. `startup` takes its position before restart recovery and runs it on its own thread.
- `conversation_settings_get` (`api/conversation_settings.rs`) reports every setting of a chat with its current value and its source (`conversation`, `group`, `character`, `launch` or `app_default`), resolved the way a turn resolves it; a value whose source is `conversation` is the chat's own and can be reset. A group chat lists its members as the chat uses them (enabled, muted, model), including a member the group gained that has no row yet, under the participant id its row will get, and says whether the member list, muted flags and models are the chat's own or the group's.
- `conversation_settings_update` takes ids and plain values and `apply_settings_change` (`conversation/settings.rs`) resolves them into the snapshots `CurrentConversationSettingsPatch` needs (a persona, prompt, lorebook, model or scene snapshot is staged in the update's transaction, under an artifact id derived from the conversation and the source revision), refusing an unknown or archived source as `InvalidInput` naming the field. A prompt must be an active document of the slot's purpose: any direct-chat selection purpose for a one-to-one chat, a conversational or roleplay group prompt for a group's two slots. The author note is trimmed and a blank one removed; an empty lorebook list turns the chat's lorebooks off; `reset` of a field follows the group, character or launch again, and `reset_members` and `reset_member_models` return the members to the group. The update runs under the settings revision the caller read (none while the chat has no settings of its own): a stale one is `Conflict`, and the same change against the same revision replays. It bumps the conversation, so `ConversationChanged` follows.
- `conversation_rename` trims the title and refuses a blank one; `conversation_archive` and `conversation_restore` change the lifecycle and succeed without a write when it already is the target.
- `conversation_participant_add` adds a character to a group chat through `add_group_member` (`conversation/participants.rs`), which snapshots the character like a launch member or enables the row it kept, idempotent by the request's key; the chat owns its member list afterwards, and when it followed the group until then the add's transaction writes every other member's enabled flag, as the group had it at commit, into its row. `conversation_participant_update` enables, disables, mutes or unmutes a member or sets or resets its model through `update_group_participant`: each aspect it touches becomes the chat's own, the other members keep in their rows what they followed from the group, and a change that would leave no enabled, unmuted member is `InvalidInput` naming `conversation.group.active_member` (the conversation command checks it against the group as it stands at commit). It is idempotent by its `client_operation_id`: the same key and request replays, another request under the key is `Conflict`. Both first give every group member the chat follows a row.
- `conversation_delete` (`api/conversation_delete.rs`) deletes a chat and the media it alone used. When a reply or memory cycle is still running, it requests their cancellation (a queued reply is settled at once, a running one through its token, a memory cycle through the token it registered under its job), then waits for them to settle: it tries the purge again after each committed job or conversation change, never on a timer. Work that can no longer run is settled on the spot: a live turn whose job already ended (or has none) through `settle_unrunnable_turn` (a turn another write moved on meanwhile, such as a job attached, is read again at the next step), and a memory attempt behind an ended job through `settle_memory_attempts_of_ended_jobs`. `DELETE_SETTLE_LIMIT` (30 s) is only a last resort for a runner that ignores its token: then the delete answers `Busy`, which normal use never reaches. Deleting a deleted chat succeeds. If the app stops between the cancellation and the purge, restart recovery settles the cancelled work and the next delete completes.
- Message operations (`api/messages.rs`) all take `expected_revision` and a `client_operation_id`: the same key and request replays, another request under the key is `Conflict`. `message_edit` trims the text (blank is `InvalidInput` naming `text`) and keeps only the media `keep_media` names, through a superseding revision; a scene message is marked edited, and a message a running turn writes is `Conflict`. `message_delete` tombstones one message and keeps the ones after it, unless another branch also shows it: then it forks a branch at the message's parent, copies the selected branch's later messages into it without the deleted one and selects it, answering `Tombstoned { removed }` or `Branched { branch_id }`; deleting the scene message turns the scene setting off in the same commit, in the tombstone case only. `messages_delete_after` cancels the chat's memory cycles and waits for them to settle (committed changes wake it, never a timer), then runs the delete-after described under Delete-after, answering `Tombstoned { removed }` or `Branched { branch_id }` with the new revision. `message_pin` sets the flag, `message_candidate_select` chooses a reply variant, and `message_scene_select` switches the starting scene from the scene message: the setting and the re-rendered, not-edited message commit together (`select_scene`). `message_revisions` and `message_candidates` page the stored histories. A conversation whose owed delete-after rewind failed reports `memory_blocked` (with a failure code) on its view and list row, and `memory_rewind_retry` retries the rewind now, answering `NothingOwed`, `Completed` or `StillFailing`; the change feed announces the chat when the failure is recorded or cleared (triggers on the owed-rewind table write `conversation_changes`).
- Message reads (`api/messages.rs`): `conversation_search` streams the selected branch's timeline page by page and matches the trimmed, Unicode-lowercased query against the shown text of visible user, reply and scene messages, oldest first, without loading the whole chat or capping it; an empty query answers an empty page without a read. `conversation_pinned_messages` pages the pinned visible messages the same way, and `conversation_message_count` reuses the list row's count. `conversation_messages_around` anchors a page at a message of the selected branch (`timeline_anchor`) and returns the cursors that continue in both directions; `conversation_messages` also reads newer pages with `after_cursor`.
- `characters_list` (`api/characters.rs`) pages active characters with their avatars for the launch picker.

The generation worker (`ConversationGenerationWorker`) runs queued generation jobs one at a time. `run_once` asks `PreparedConversationGenerationJobRunner::next_queued` for the next job. `next_queued` fails a queued job whose turn or attempt cannot be resolved instead of stopping the queue, and leaves the turn it names alone (a live attempt either owns another job or is still being admitted; restart recovery settles anything left behind). A job `admit` created but has not attached to its attempt yet is skipped for that scan, not failed. The worker runs the job with `execute_with` and a one-hour lease (longer than any provider request); only once the job is claimed, and when its turn has a sink, it sends `Started`, registers an `InferenceRuntime` stream and forwards every text or reasoning delta as `Delta`. A job that could not be claimed or had already ended counts as not run. Afterwards it drains the stream, reads the turn and, once the turn is terminal, sends `Completed` (the reply's message id), `Failed` (the turn's failure code) or `Cancelled` and emits `GenerationSettled`. A stream is dropped whenever its turn settles by any path: a worker run, a queued cancel, a failed schedule, a job failed as unresolvable (each `run_once` ends the streams of turns settled meanwhile) or restart recovery. An interrupted attempt recovered into a child, or a retried job, keeps its sink for the next run. `run(shutdown)` loops until the shutdown future completes (a job already running finishes first; `begin_shutdown` cancels it). It never polls: an idle worker sleeps until a send, a cancellation or another scheduling path wakes it, and a retried job is queued again at once, so no generation job waits for a later time. A step that fails (such as a storage error) is retried after a delay that doubles from 250 ms to 30 s and resets after a step succeeds; the job runner shares this loop (`api::worker::drive`). The runner calls repositories synchronously, so the worker gets its own thread and runtime. The post-turn memory scheduler is not wired to the worker yet.

Jobs (`api/jobs/`):

- `jobs_list` pages jobs most recently created first, filtered by kinds, states and subject (empty lists match everything), through the `JobCatalog` read model in `lettuce-database`; the cursor is keyed on creation time and id, so it stays stable while jobs are created. `job_get` reads one. A `JobView` carries kind, subject, state, the current stage as `label_code`, progress (bytes, items or permille of the stage), times, the failure code and whether it is retryable, and a typed result where the outcome has one (an installed artifact, an asset, a turn, a conversation, a group, a character or a model). A local model job also carries its `subject_detail` (the repository file a download installs, the model an Ollama server pulls, the folders a move goes between) and its result (`ModelInstalled` with the model path and the llama.cpp model it became, `ModelPulled`, `ModelsFolderMoved`), read from the detail the database keeps next to the job (`local_model_jobs`), so they survive a restart and travel in a v2 backup with the client operations and refusals (`JobBackup`); a download Hugging Face refused names why in the failure's `hugging_face`.
- `job_cancel` records a user cancellation. A queued job is cancelled at once and its install work dropped; a job this process runs is signalled through its cancellation token and settles through its coordinator; a job another host runs keeps the request for its runner; an ended job is left alone. Conversation turns are `Unsupported` here, since `generation_cancel` settles the turn with its job.
- `job_watch` attaches a `JobEventSink`. It reads the job while holding the watch registry, so no change slips in between: a live job's watch gets `Progress` with the current state first, then every change; an ended job's watch gets only its terminal event (`Completed`, `Failed` for failed or interrupted, `Cancelled`). A terminal event is sent at most once per watch. LLM features that stream send `TextDelta` to the watches of their job through the runner's `JobProgressSink`.
- Progress reports the current stage as `label_code`, or `verify` while a download whose bytes have all arrived is checked, and the job change feed adds the download speed in bytes a second from the job's previous published progress.
- The job change feed (`JobFeed`) follows `JobCatalog::job_changes_since`, the database's monotonic record of changed jobs, so it sees every change any host writes. It never polls: the database raises `on_job_change` after each committed transaction that changed a job, the feed then waits 250 ms to gather further changes and publishes each changed job once, with its latest state, as `ApiEvent::JobUpdated` and to its watches, which bounds one job to four updates a second. `startup` takes the feed's position before restart recovery, so the jobs recovery settles are published too. A watch whose stream is closed (`JobEventSink::emit` returns `false`) is dropped. The listener belongs to the open `Database`: if the process ever swaps its database (a restore or legacy cutover without a restart), the host must register `on_job_change` on the new one and restart the feed from that database's position.

The job runner (`JobRunner`) runs every job kind the conversation generation worker does not, through a `JobHandler` per kind (`JobHandlers::standard`; a kind gets its handler by adding it there). A handler names the lane a queued job runs in, or none while this process cannot run it (the job stays queued), and claims it through the kind's coordinator; the claimed job then runs on its own task until it settles. Jobs in one lane run one at a time and lanes run concurrently. Like the generation worker, a job only counts as started once claimed and an idle runner never polls: it sleeps until a new job, a cancellation or a finished job wakes it, or exactly until the earliest time a handler reports for a queued job (`JobHandler::not_before`; no install carries one), every job's token is linked to the context's shutdown token, and a job cancelled between its claim and the token's registration is signalled at once. On shutdown the runner waits for its running jobs, which the cancelled token stops.

`ArtifactInstallHandler` runs `ArtifactInstall` jobs from the `InstallWork` an admitting call hands to `admit_install` (a request for an install already queued or running joins that job). Embedding pins and setup choices commit with their job and reconstruct queued work after restart. Other artifact plans stay in the runner's memory until the job ends. Artifact installs run through `ArtifactInstallCoordinator::run_then`, whose install stage is the finisher the work names (`InstallFinish`): none for the upscaler; for a GGUF model nothing more than the file joining the library, or `register_downloaded_gguf` when the request asked to create a model (legacy's `create_model_when_finished`) with the setup it chose; `finish_runtime_install` and then `register_catalog_model` for an engine build whose queued variant is complete, `register_catalog_model` for a catalog variant, `finish_hf_bundle` for an image bundle, `record_civitai_lora` for a CivitAI LoRA and `EmbeddingModelCoordinator::complete_install` for an embedding family (which runs `finish_embedding_install`); a failing finisher fails the job. The Thymos install finishes after the job succeeded, since `finish_companion_emotion_install` refuses while a Thymos job is active. An embedding or Thymos install drops the loaded models when it starts and again when it ends, so the next use loads what is installed then. Whisper and Kokoro model and voice downloads run through their own coordinators, which record the installed manifests. GGUF, stable-diffusion.cpp, CivitAI, Hugging Face bundle, Whisper and Kokoro downloads share one sequential lane, like the legacy download queue; the embedding and Thymos installs each have their own. A download source that cannot be built (no client, an unreadable saved token) fails the job as `ResourceUnavailable`, retryable; install work that does not match its job fails it as `InvalidInput`; a claim that fails on job storage leaves the job queued and the runner retries it after its error delay; a job whose cancellation arrived between its claim and its start is cancelled. Downloads come from `InstallSources`: over the network signed in with the saved Hugging Face token, or the CivitAI token for a LoRA. A Hugging Face file whose request is refused (401, 403, 404, 429) or never answered fails the job with a typed reason (`hf-token-missing`, `hf-token-invalid`, `hf-gated`, `hf-not-found`, `hf-rate-limited`, `hf-offline`), which the view turns into an `HfFailure`; Whisper and Kokoro downloads type a refusal the same way, and the job's Hugging Face repository (from the install's plan or model source) is kept with the failure (`hugging_face_job_refusals`), so `GatedAccess` names the repository for every install kind.

`ModelPullHandler` runs Ollama pulls (`ModelPull` jobs), each in its own lane, so pulls run next to each other and next to downloads as legacy ran them. The pull's account and model are stored with the job, so a queued pull survives a restart. Progress is written at most every 150 ms after a progress line, and cancelling the job drops the stream, which stops the pull at once, also while the server sends nothing; the failure names an `OllamaFailure` (the view reads it from the job's label and, for a server error, the server's words kept with the job): offline (retryable), credentials unavailable or refused, the server's error, or a stream that ended without success (`ollama-pull-incomplete`). `ollama_models_list` and `ollama_model_delete` return the same failure in `ApiErrorDetails::Ollama`. `ModelsFolderMoveHandler` runs a models folder move (`ModelsFolderMove`) in the download lane, so no download writes into the folder while it moves; it checks again that no install writes into the folder and llama.cpp holds no model from it and blocks the folder in llama.cpp's file registry (`block_llama_folder`, refused like the admission when a model there is held or queued), so a chat that asks for a model in the moving folder fails as unavailable (`LOCAL_MODEL_FOLDER_MOVING`) until the move ends, the same Busy rule the move applies to loaded models, then `set_llm_models_dir` copies on a blocking thread while the job renews its lease: a manifest in the destination names the move, the source and each entry it copies with its size, file count and newest modification time, files copy in 1 MiB chunks, the job's cancellation (the user's or shutdown's) is checked between files and chunks and removes the copies whose originals are unchanged, and the model paths and the folder setting are saved in one transaction before the originals whose copies are complete and the manifest go; a manifest that cannot be removed then does not fail the committed move. Failures are typed (`models-folder-destination-inside-source`, `models-folder-destination-not-empty`, `models-folder-copy-failed`, `models-folder-paths-unsaved`, `models-folder-busy`). At startup (`recover_local_model_jobs`) a queued move is cancelled, since a move never runs unattended. Only the newest unresolved move is resolved from its manifest: a copy goes only while its original is still there with the recorded size and time and every copied byte matches its corresponding original (a partial file must be an identical prefix), and once the move committed (the stored folder is the destination) an original goes only when its full contents match its retained copy; entries it cannot prove are kept and reported. Older unresolved moves are marked superseded, and a resolved move's leftover manifest is removed without being applied (`discard_models_folder_manifest`). Queued GGUF downloads resume from their stored plan and setup (`resume_gguf_install`) when their folder is still the models folder in use, else they are cancelled (a backup restored from another machine); queued pulls resume from their stored detail.

Optional models (`api/models.rs`): the embedding model and the emotion model (Lettuce Thymos) are optional; a user who never uses dynamic memory or companion chats never downloads them. Nothing loads them at startup. A `ModelLoader` (`InstalledModels` in production) says whether one is installed, prepares ONNX Runtime (`OnnxRuntimeInstaller::ensure`, which fetches it only when the device has none) and loads it; the context's slots keep a loaded model, remember that none is installed, and forget both on `models_changed` (install, switch or removal). `required_models` says which models a conversation needs from its live state without loading anything: a companion (by `companion_clock_context`) needs the emotion and the embedding model, dynamic memory (by the memory host's own gate, `dynamic_memory_on`) the embedding model; a one-to-one chat whose character no longer exists is not a companion, as generation treats it. Lists and open views report `missing_models`, the required models whose install records say they are not installed (`ModelLoader::installed`, read once per request); they never load a model. `conversation_send` loads the required models once: a model that is not installed refuses the send with `ModelRequired`, one that cannot load with `ModelUnavailable`, both naming the model in `ApiErrorDetails::Model`, before anything is written. A retried send whose operation was already accepted replays without that check, so it still replays after the model was removed; a different send under the same key is `Conflict`. Every operation that begins a turn checks exactly the models it uses (`TurnOperation`, `operation_models`): a send the chat's full requirement, regenerate, continue and retry the embedding model when the chat runs dynamic memory, and none of them the emotion model, since only a send classifies. Chats that need neither are unaffected. The engines the API hands out (`ApiEmbedding`, `ApiEmotion`) load the model at their first call and report `requires_model`, so a memory cycle whose embedding fails is failed as `CapabilityUnavailable` (`embedding-model-unavailable`, shown as the job's `model`) instead of keeping memories without vectors, a companion send whose classification fails is refused as `ModelUnavailable` instead of taking the neutral update, and one without an emotion engine at all as `ModelRequired`, and a turn whose memory backfill or retrieval embedding fails fails with `GenerationFailureCode::EmbeddingUnavailable` instead of running without memories. Engines other callers pass keep the lenient behavior.

## Startup and shutdown

`api::startup(context)` is the host's start order. Before it returns it takes the job change feed's position, runs `recover_after_restart`, finishes the memory rewinds a delete-after still owed, detects a legacy database and records the legacy v4 embedding files where they are (`adopt_legacy_install`, local, no download and no load; an adoption forgets a remembered missing model), so the host serves commands and resolves models only afterwards. Then, on a startup thread, it runs the memory host's and the companion follow-up host's `resume_after_restart`, recovers queued installs (the Thymos install its hint describes is taken up again; every other queued `ArtifactInstall` is cancelled, since its work ended with the previous process), sweeps orphaned media files, and last starts the workers, each on its own thread with a current-thread runtime: the conversation generation worker, and the job runner with the job change feed. Startup downloads nothing and loads no model. `ApiWorkers::stop` tells them to take no new work, calls `begin_shutdown`, stops the local diffusion server, records the counted active time and then joins every thread (a startup step still running is cancelled through the shutdown token), the order legacy used; the host forwards window focus (and on mobile, background and resume) to `app_focus_changed`, and losing focus writes the counted active time; no timer flushes it.

`AppBackend::open(path, now)` is the only supported way to open the production database. It opens and migrates the SQLite file, bootstraps the built-in prompt catalog, clears the cached smart-offload layer count (`actualGpuLayersUsed`) from every llama.cpp runtime report (free VRAM differs between sessions; a failure is logged and the open continues), and returns the backend with the typed `BuiltInPromptIds`. A host therefore cannot serve an initialized database without the app prompts. `open_in_memory` gives tests the same guarantee. `AppDatabaseLocation::active_path()` names the file to open; a restore switches it.

Before any worker starts, the host calls `recover_after_restart(now)`. It releases every claim the previous process held, cancels every waiting conversation generation job (reason `Recovery`), and settles each live turn so its conversation accepts new turns again: a turn that had not started or was being cancelled is cancelled, a recovering turn fails with `RecoveryUnavailable`, any other is interrupted (usage outcome `Interrupted`); running tools are interrupted and requested or validated ones cancelled. Nothing is run again. Work a user asked for is settled rather than rerun: a queued staged lorebook planner or writer without a saved attempt fails with `AppStopped` through its own settlement (so a new batch can start, and a failed planner can be retried), one with a saved attempt stays queued so the user's next action finishes it without new inference, a planner not yet planning is left alone, and refine runs without an attempt, coherence, lorebook entry and keyword jobs, one-shot helper jobs, speech jobs and image jobs are cancelled. Every ended image generation whose record is still pending is settled (idempotently, so a failed reconcile retries next start). If a claimed settlement fails, the job is failed as `LeaseLost`. A job or turn that cannot be settled is logged, reported and skipped. Other job kinds keep their recovery policy (`Restart` and `Resume` jobs are queued again) and wait for their drivers: the memory host's and follow-up host's `resume_after_restart` run next.

On exit the host calls `begin_shutdown`, which cancels every running inference (`InferenceRuntime::cancel_all`) and stops the local diffusion engine from taking or continuing work, then `shutdown().await` to stop its server process.

`AppBackend` owns the process-wide runtimes: the `InferenceRuntime` shared by every provider call (stream receivers and cancellation tokens), the Whisper runtime, and on desktop the embedded llama.cpp worker, started on first use and attached to the provider runtime, and the optional local diffusion engine (`with_local_diffusion`). The two local runtimes exclude each other: the image server unloads llama.cpp before it starts, and llama.cpp stops the image server before it runs.

## Built-in prompts

All prompt text the app sends lives in the built-in catalog, `resources/built-in-prompts/v1.json`, embedded with `include_str!` so bootstrap and reset work from the binary on desktop and Android without installation paths or writable files. It holds the chat templates (`prompt_app_default`, `prompt_app_local_roleplay`, `prompt_app_companion`, the two group templates), every feature prompt (memory summarizer and manager, reply helper, lorebook writers, avatar and scene prompts, design references, companion Soul writer, growth and consolidation) and the runtime text documents (`prompt_app_chat_runtime`, `prompt_app_memory_runtime`, `prompt_app_lorebook_runtime`, `prompt_app_companion_runtime`, `prompt_app_creation_runtime`, `prompt_app_creation_helper`, `prompt_app_group_speaker_selection`). Rust decides whether and where a piece of text goes in; the entry decides what it says, its role and depth. A user edit or a disabled entry is honoured (runtime entries are not system-prompt entries, which `LegacyV1` would render even when disabled).

`BuiltInPromptService` reconciles unedited seeds at startup and resets one or every protected prompt on request. Consumers keep the returned `BuiltInPromptIds` instead of database UUIDs. The catalog keys and entry keys are stable identities; names and content are editable, purpose and lifecycle protection are not. The adjacent `v1.snap` pins a canonical digest for every entry (key, role, content, scheduling, conditions, payload, system-prompt flag), so a change shows up on the exact entry rather than as a catalog checksum. Empty sections are expressed as entry conditions: the default template's `entry_world_info` requires `hasLorebookContent` and `entry_context_summary` requires `hasMemorySummary`.

Runtime text is read live and rendered once per turn. A key missing from a stored document (a user-edited copy kept across a catalog update) renders the bundled text; a disabled entry stays off; a missing runtime document fails the turn with `RuntimeTextUnavailable`. Protocol formats (`<time>…</time>`, `[message:ID]`, `[id] text`, `role: text`) are data formats and stay in code.

## Launching a conversation (`launch/`)

`ConversationLaunchPlanner` resolves a launch request against the authored graph, copies every resolved source into an immutable snapshot document, and hands the closed `PreparedConversationLaunch` to the conversation creator. All identities derive from the operation key, so a retried request lands on the same conversation. `prepare_direct` and `prepare_group` serve both the UI and the legacy importers.

- The prompt a launch records follows `launch::policy`. A companion character uses the companion chain (`companion_prompt`): its companion template, then the app default prompt, each only when it is an active companion-chat document, then the bundled companion prompt; a starter's prompt is ignored. A direct character uses the starter's prompt (a direct-chat or group document, `policy::STARTER_PROMPT_PURPOSES`), then its direct prompt, then `direct_app_default_prompt` (the app default when it is an active direct-chat document, else the bundled default, disabled only when that is missing too). An explicit starter prompt fails on any resolution error, an inherited direct prompt fails when dangling or of another purpose, and an archived inherited one falls through to the app default.
- A launch that found no default persona snapshots none, so the chat follows a default set later. A launch that turns the persona off records it as the conversation's own disabled persona (`CreateConversationPlan::current_settings`), which stays off.
- Every manual or dynamic memory policy gets its conversation memory space in the launch transaction. Direct launches freeze the global direct memory policy; group launches freeze the group override when present and otherwise the direct policy. Generation uses those frozen values, so later global changes do not alter retrieval, access mutation or tool-round policy for the conversation. An older dynamic snapshot without the policy stays readable but fails closed when generation needs it.
- A group launch freezes the dedicated speaker-selection model when configured, otherwise the app default, with its exact model and account revisions and protected artifact. Companion characters join groups as ordinary members; companion state, prompt state, scheduled notes and the clock stay direct-only.
- A direct companion launch freezes the validated companion defaults and the effective persona scope in a non-serializable prepared launch. The database commits the conversation, artifacts, operation and outbox, fresh session emotion, the carried character and persona relationship and the next continuity episode together, closing the prior open episode. Exact retries revalidate the initial-state request without resetting relationship continuity or advancing the episode.

## A chat turn (`generation/`)

Launch snapshots record what was selected; a turn reads its sources live. The flow for one reply:

1. Begin. The UI command calls `begin_send`, `begin_continue`, `begin_regenerate` or `begin_retry` on the conversation repository. A direct companion send goes through `CompanionTurnCoordinator` instead (see Companions), which commits the same send plus the companion state transition in one transaction.
2. Schedule. `ConversationGenerationDispatchCoordinator::schedule` admits the returned `BeginGeneration` as a `ConversationGeneration` job keyed by the attempt's idempotency key and attaches it.
3. Claim. A worker calls `PreparedConversationGenerationJobRunner::execute_next`, which takes the oldest highest-priority queued generation job, resolves its creation event back to the turn and attempt, and claims it with the caller's resource availability and a shared cancellation token. One call handles at most one job and returns `Idle` when none is queued; polling cadence belongs to the host. `execute` runs one known turn the same way, and a succeeded job returns its candidate and usage as an exact replay.
4. Reconstruct input. If an initial dispatch request was already admitted for this attempt or its interrupted parent, it is reused unchanged (profile, context, tools and media grants), with only the attempt, job and stream sink swapped. Otherwise the runner builds it: it loads the turn and the whole branch ancestry (timeline pages arrive newest first and are reversed), trims a finalized replay back to the turn's source message, resolves the speaker for a group turn, resolves effective settings and the live model, retrieves memory, assembles context and derives unique media grants from it.
5. Run. `ConversationGenerationJobRunner` stages `Preparing`, prepares the turn with the resolved model and attributions, stages `Running`, dispatches through `ConversationInitialInferenceCoordinator`, records usage and finalizes the reply, with the usage timestamp frozen to the dispatch checkpoint. Every mutation it owns uses an operation token derived from conversation, turn, attempt, job and step, so a rerun replays instead of conflicting. Before each stage append it reads the latest durable checkpoint sequence, so streaming progress and reopen never collide with runner stages.
6. Settle. Success settles the job. Cancellation runs the two-phase turn cancel. Failure goes through `fail_generation`. A pending dispatch is interrupted and recovered into a child attempt with its own job, linked as a child of the parent. Non-success settlement records a real usage event from the complete dispatch evidence (known counters only when every admitted response reported them, else an unavailable reason), so no attempt references an invented usage id. A recovered child on an already prepared turn goes straight to `Running`. Turn-side settlement errors schedule a job retry instead of leaving the claim running.
7. After the turn. The host enqueues the conversation on the post-turn memory scheduler (see Memory).

The caller creates the turn and decides when to run it; the only background loop for chat is the API's generation worker (see Application API). Only the stream sink and the prompt runtime values are caller-supplied, and the sink stays outside the dispatch fingerprint, so a replay may use a new sink without another provider call. Every turn reads live global settings.

Streaming is a preference: a caller's stream sink is used only when the account has streaming on and the model does not declare streaming unsupported, and the provider adapters stream only when they support it; a model that cannot stream answers in one piece. Chat replies declare no tools; a reply carrying tool calls is rejected as `ProviderRejected`. A regenerated candidate's ordinal comes from the prior candidate, not the provider's response index. Unreadable settings documents fail the turn instead of retrying it.

### Initial dispatch

`ConversationInitialInferenceCoordinator` reloads the turn, checks turn, attempt, job and request identities, and requires the request's model and context attributions to match the prepared turn. It admits a pending checkpoint before calling the provider, bound to the job usage event that keeps the raw response. The response, an invalid response, a provider failure or a cancellation seen after the response settles the checkpoint once; a later call with the same request replays the stored outcome or error without another provider request, including after finalization or reopen. Changed context, profile, tools or media grants conflict. A concurrent caller, or one that finds a pending record whose settlement never completed, gets a pending error, and the attempt follows interruption and recovery; the child dispatches fresh while the parent record stays. Cancellation before admission leaves no evidence.

A cancellation after visible text or a whole reply image has streamed settles the streamed reply with a `Cancelled` finish reason (the adapters return the text, reasoning and images received so far), and finalization stores it as the stopped reply.

### Retries and live edits

A retry reads whatever is saved when it runs. An attempt that already admitted its request resumes that request unchanged. A recovery child resolves its model and builds its context afresh and records them on the turn in place of the earlier attempt's, so a live edit between attempts never makes the retry conflict. An attempt resumed after preparation but before admission, whose inputs changed meanwhile, sends nothing and ends pending, and the recovery child rebuilds. Each attempt's admitted request keeps the model, prompt, lorebooks and memory that attempt used; the turn records its latest attempt's.

### Live sources

`generation::live_sources` re-reads the conversation's persona, characters and group each turn:

- Model: a direct chat without its own override resolves its chat model live: the character's current default model, then the app default. A live model whose revisions differ from the launch snapshot gets a conversation snapshot, stored and attached to the conversation in one write (`ConversationArtifactStore::attach_snapshot`), and the turn records the model it used.
- Prompt: `live_direct_prompt` follows the companion chain from the live character and app settings for a companion chat (so a chat launched before its character became a companion, and a template changed after launch, follow the current template). Any other direct chat follows `launch::policy::direct_prompt`, and nothing is fixed at launch: the chat's own current override, then the current prompt of the starter the chat launched from while that starter still exists and has one, then the live character's direct prompt, then the app default chain. Each step is read when the turn runs, so editing a prompt's content, pointing the character or the starter at another prompt, or removing the starter reaches existing chats on their next turn. A missing, archived or wrong-purpose prompt falls through to the next step, and a prompt the chat disabled yields none. Branches share the conversation and resolve the same way. The override resolves when it is an active direct-chat, companion-chat or group document (`policy::DIRECT_SELECTION_PURPOSES`), the starter's prompt when it is an active direct-chat or group document (`policy::STARTER_PROMPT_PURPOSES`, the same rule the launch applies), and the character's prompt only as a direct-chat document; render values a purpose does not admit are left out instead of failing. Feature prompts never qualify.
- Group prompt (`live_group_prompt`, `policy::group_prompt`): the conversation's override, the speaker's current group prompt for the chat mode, then the group's, each only when active and of the mode's purpose, else the bundled group prompt; a disabled prompt yields none.
- The app default prompt is selected with `Database::set_default_prompt_document` under the settings revision.
- Resetting a chat prompt means `PatchValue::UseLaunchDefault` (back to the live chain), not `Clear`, which stores a disabled prompt.
- Launch and override snapshots only record which prompt was selected; their content is never rendered for a one-to-one turn, and the launch prompt is never used to resolve one. Prompt attribution carries the live document's id and revision.
- Lorebooks: a direct chat uses its own selection (a current override or a starter's explicit books), else the character's current enabled bindings followed by the current persona's. A group uses its own selection or the group's current bindings first, then the speaker's current bindings unless the group disables character lorebooks; an empty or disabled group selection removes only the group's books. Each tier orders active entries by display order, creation time, then binding order, and a group turn keeps an entry's first occurrence. The turn records every book with the revision read and the activated entry ids.
- Persona: a one-to-one chat uses its chosen persona, else the current default (also when the chosen one is gone or archived). A group uses its own persona, else its launch's explicit one, else the group's current selection; a missing persona is none.
- Characters and groups: every character body is its current record; `{{group_characters}}` and `{{@"Name"}}` use the group's current members in cast order, or the chat's own enabled members when it owns its member list. A group conversation's settings (`live_sources::live_group`) are its own values when set, else the group's current ones, else the launch values when the group no longer exists: chat mode, character-lorebook switch, speaker selection, persona, prompts (one slot per chat mode), lorebooks, starting scene and background. A conversation-mode group turn sends no scene; a roleplay turn follows the group's current starting scene unless the chat chose its own.
- Participants (`live_sources::effective_participants`): a group chat that does not own its member list treats a character as enabled while it is one of the group's current members (a removed member's row and messages stay), and one that does not own its muted flags mutes as the group mutes; without a group the launch values apply. Speaker selection, mentions and the cast read these values. A member the group gained after launch gets its participant row when a send needs it (`ensure_group_members`, under one operation key per member, so retries and racing sends create it once).
- Group member models (`live_sources::member_model`): the chat's own model override, else the member's own model when the chat owns its members' models (or its group is gone), else the group's current model for the member, else the character's current default model, else the app default; a live model gets a conversation snapshot like a direct chat's.
- Memory mode (`live_sources::live_memory`): the chat's own setting, else the live character's memory mode (one-to-one) or the group's current one, else the launch value. A mode equal to the launch mode keeps the launch settings and their frozen policy; another mode takes the current global policy. Generation, the memory host's gate and `required_models` read it the same way.

### Context assembly

`ConversationContextAssembler` is the last application step before provider I/O. It renders the prompt through `lettuce-context` and adds every section the template does not carry from `prompt_app_chat_runtime`: summary, key memory, world information, author note (with a group variant), companion state and scheduled-note fallbacks, the swap-places note, and the regenerate, continue, group begin and group continue-same-speaker instructions. It renders with the turn's swapped names, so under swap places `{{char.name}}` is the side the model plays. The author and swap notes name `{{persona.name}}` (the persona, or the user's display name).

- History goes in conversation order (the parent chain), never sorted by time, so a clock moved back keeps the whole context. In-chat entries and runtime sections count depth within the conversation messages only; a depth beyond the history lands right after the system prompt.
- The history window is `summary_message_interval` for dynamic memory (the group override for groups) and `manual_mode_context_window` otherwise, used as configured. The context request carries only pinned and scene messages, the source message and the recent window, so the omitted-message count reflects the trimmed input. The lorebook scan and the prompt keyword conditions both read the last `lorebook_scan_depth` messages (from the settings each turn; the lorebook scan also reads the latest user message), and they and the prompt message count use the whole branch.
- A condensed direct prompt merges every relative entry and relative runtime section into one system message and every depth-zero in-chat entry except conditional and interval ones into one turn-context message; a condensed group prompt merges everything into one system message.
- Identity tokens: `{{user}}` is the persona title, `{{char.desc}}` the definition else the description, `{{persona.desc}}` the persona description. Lorebook text, summaries, memories and author notes resolve their tokens before rendering, and every message of a one-to-one request resolves `{{char}}`, `{{persona}}` and `{{user}}`. A one-to-one chat with no scene drops entries naming `{{scene}}`. The reasoning condition follows the turn's reasoning setting. `{{group_characters}}` renders one catalog line per member other than the speaker (definition, else description, else name), and renders empty in a direct chat. `{{@"Name"}}` in a group's starting scene becomes the member's name. Group transcripts prefix the user's and other characters' messages with `[Name]: ` from `runtime_group_message_prefix`.
- Scene image protocol: the default template's `entry_scene_image_protocol` and `_local` entries require the `sceneImageProtocol` fact, which direct chats set only when scene generation is on and the scene image model resolves (`image_feature_model`), choosing the variant for that model. `sceneGenerationEnabled` and `avatarGenerationEnabled` carry the settings in every chat. `isSceneGenerationLocalImageModel` and `{{lora_keywords[...]}}` follow the resolved scene model whether or not scenes are on: a subject names its LoRA's trigger keywords (blank for a LoRA without any) or the `scene_lora_primary_subject` / `scene_lora_secondary_subject` filler. An unreadable character or persona counts as having no LoRA.
- Pure mode: chat and group prompts get the saved level's `{{content_rules}}` text from the chat runtime catalog, and `default_character_rules` gives a new character the base and level rules.
- Companion chats get the companion state block and scheduled notes (see Companions). Roleplay and group assembly never read companion state; missing or corrupt companion state fails assembly.

### Memory in the prompt

- A direct chat launched with dynamic memory runs as manual memory while the global `dynamic_memory.enabled` switch is off; groups follow only their memory mode.
- Manual memory reads every active item of the conversation's space in stored order and renders `- text` lines, with no summary, tools, embedding, promotion or access changes. Its root revision is the turn's memory attribution. A non-empty `selected_revision_ids` fails closed.
- Dynamic retrieval embeds the latest visible user message (or the last two visible messages; a group regeneration leaves out the reply being replaced) and selects current projections with the threshold, the x0.7 cold penalty, category diversity and the recent and frequent fallbacks. Direct Smart retrieval restores score order after the category-overflow fill, then fills empty slots with the newest and most-accessed unselected hot memories; group Smart retrieval reserves up to two slots for those hot picks first. Equal scores keep memory-space order. Companion Smart retrieval adds lexical-overlap and sequence-anchor bonuses after selection, reordering lines without changing the set.
- Scores go through the active embedding model's `SimilarityCalibration` before the cold multiplier and threshold. v4 keeps raw cosine and `min_similarity` (unset means 0.35). Eidos compares its calibrated score with its published default threshold (0.50), falling back to its published fallback (0.35) when nothing reaches the default, unless `min_similarity` is set. A zero-norm vector scores 0; a NaN component never matches. Semantic duplicate evidence compares the calibrated score strictly above the duplicate threshold and stores that score.
- Before the query is embedded, every memory without a ready vector for the current model and text is embedded and stored (see Embeddings). An unavailable model leaves them for the next retrieval and retrieval continues without keys; a failed store is only logged. The call follows the job's cancellation.
- Temporal queries: for a direct companion chat with time awareness, `temporal_query` detects a calendar phrase against the clock's effective now; when found, only memories observed inside that half-open window are candidates, the threshold drops to -1 and the recent and frequent slots are skipped, while the cold keyword fallback still searches the filtered set. Calendar arithmetic is checked, so an overflowing amount yields no range.
- A non-empty selection records one retrieval-access receipt under the attempt (cold promotion, access count, time) without advancing the revision; the revision read is the context attribution. A rebuild of the same attempt reads the selection back from the receipt. Terminal replay skips input reconstruction and so repeats no embedding or access.
- In a dynamic direct or companion chat, `{{key_memories}}` and `HasKeyMemories` use only the memories retrieved for the attempt (send, continue and regenerate all retrieve), each with its observed-at suffix. Templates without the placeholders get depth-0 `# Context Summary` and `# Key Memories` fallbacks, suppressed by any raw entry naming the placeholder. Bullets, the `observed DATE, RELATIVE` note and the relative-time words render from `prompt_app_memory_runtime` (buckets computed as a typed `RelativeTime`); only the memory text has a leading `- ` stripped. Groups put `Important facts to remember in this conversation:` (`runtime_group_key_memories`) plus the retrieved items into `{{key_memories}}` and get no fallbacks, and a group's `{{context_summary}}` is the stored summary in manual mode too. A one-to-one send outside dynamic memory also adds the "Relevant memories" block (`runtime_relevant_memories`) first among depth-zero entries, so manual memories appear both in the Key Memories section and in that block.

### Time

`companion_clock` decides whether a direct chat is a companion chat (its live character is a companion, or it has companion state) and exposes the session clock, which counts only while time awareness is on. Generation renders every unset time placeholder from the clock's effective now, sets the time-awareness fact that gates the catalog `# Time` entry, and formats memory lines against the clock; group prompts get these time values too. With time awareness the assembler prefixes each direct user and assistant history message with its stored `<time>` stamp, and the runner strips echoed timestamps from every text part of the final candidate before the empty-reply check (`<time>` tags and the bracket stamp anywhere, one invented leading stamp, then trim), so a reply that was only a timestamp is an empty-reply failure. The replay input constructor treats a character deleted after dispatch as no time awareness so the recorded request still recovers. A replayed attempt formats memory lines with the clock settings current at replay.

### Group speaker selection

- A stored explicit decision runs directly, muted mention targets included. A director continuation uses its forced participant and a group regeneration keeps the original author; neither records an automatic rationale. An unresolved turn fails with `SpeakerUnavailable` before dispatch.
- For a user-message send in a non-director group, a mention of an enabled character in that message becomes the explicit speaker before any automatic method, bypassing mute and making no selection call. Mentions resolve against each character's current record: display name (nickname, else name) first, then the real name. The LLM selection prompt and transcript labels use real names. A participant whose character no longer exists is ineligible everywhere and labelled "Unknown".
- Automatic selection uses the conversation's current method (its own setting, else the group's launch method). For heuristic and round robin the runner derives participation counts and the prior speaker from the active-branch timeline, stages `SelectingSpeaker`, applies the pure policy and stores the decision through `ResolveGroupSpeaker` before preparing context. Disabled participants are ineligible and muted ones excluded.
- LLM selection always uses the live group speaker model setting, else the live default model, read when the selection runs; the model must support tools. The decision records a conversation snapshot of the model revision it used, stored and attached to the conversation in one write before the call is admitted. A rerun of the same attempt first reads that attempt's dispatch row and returns its settled decision (or reports it pending) without resolving the model or rebuilding the request, so a settings change between the settlement and the recorded speaker never conflicts. The launch snapshot of the speaker model is attribution only. The prompt is the narrator prompt from `prompt_app_group_speaker_selection` (participant blocks with JSON-quoted fields, participation share, turns since each spoke, the last ten messages as 512-character previews, the quoted new user message, guidelines and a muted note), with a required `select_next_speaker` tool whose enum holds only enabled, unmuted participants. The call is admitted under its own checkpoint and usage record before dispatch. A valid call stores the participant and a bounded rationale; invalid, missing, malformed or foreign output, or a non-cancellation provider failure, keeps the usage and falls back to the heuristic; cancellation stops. No configured model, a missing model or account, or a model that cannot resolve with tools falls back heuristically without provider usage and records no model. Changing or clearing the speaker-model setting reaches every group conversation on its next selection. Settled decisions replay after reopen from the stored decision without a new call.
- The selection and generation dispatch rows are raw evidence for the same attempt; their counters overlap the terminal usage event and must not be added to it.

### Model parameters

Chat parameters resolve with the conversation's own model settings as the session layer (`ModelSettingsLayer::chat_overrides`: a set field overrides, an unset one inherits) and the global model settings as the app layer, in the order conversation, model, app; fields the resolver keeps model-only ignore the app layer.

App features use `feature_parameter_input`: the model's feature slot (`ModelProfileConfig.feature_parameters`) overrides the model, unset temperature, top_p and (when the feature has one) output cap come from the feature's `FeatureSamplingDefaults` constant, reasoning is off, conversation settings do not apply, and the app layer fills what the model leaves unset. `FeatureRequestFields` keeps the fields each feature sends: only direct help-me-reply sends top_k, the penalties and prompt caching (the scene writer sends prompt caching only); every other feature sends temperature, top_p, the output cap and context length, while Ollama and llama.cpp still get top_k and the penalties through their options. Help-me-reply (settings output cap when the slot sets none), dynamic memory (plus the llama.cpp sampler strip to top_k 40 and neutral penalties, skipped when the slot sets its own llama sampler), group speaker selection and the staged lorebook generator (generator output cap) use it directly; companion Soul writer, companion memory, lorebook entry and creation helper runs get a profile built the same way by the host. Growth and consolidation resolve the memory run's model with the CompanionMemory slot and its defaults (temperature 0.3, top_p 1.0, reasoning off, no memory sampler).

### Provider runtime

`ProviderRuntime` wraps `RemoteProviders` with the host's `SecretStore` and TLS policy, owns the shared `InferenceRuntime`, and exposes the catalog, model listing and key verification as `lettuce-contracts` DTOs. It reads the saved Pure mode level on every request and runs every provider answer through the Pure mode guard (`content_filter`). `StoredProviderMedia` wraps the local media store as the providers' `ProviderMediaSource` (`with_media_source`), so llama.cpp vision and remote providers can read attachments.

On desktop, `DatabaseLlamaHost` stores llama.cpp runtime reports and generation metrics and forwards frontend events to the `LlamaEventSink` the host attaches with `with_llama_event_sink` (logged at debug level until then). The llama.cpp commands are `AppBackend` methods: `llama_backend_devices` (integrated GPUs included), `llama_context_info`, `llama_embedded_chat_template` (loads the model on the CPU, since llama.cpp names a template for some models that carry none) and `unload_local_llama`.

### Reply media

Before finalizing, the runner stores each image on the provider candidate through its `ReplyMediaStore` (`with_reply_media`; `AppBackend::reply_media` builds `ReplyMediaAssets` over a `LocalMediaBlobStore`) as a persistent `GeneratedImage` asset with `chat_reply` provenance, content-addressed so equal bytes share a blob, and appends an `Attachment` part per image after the text. The asset id derives from the attempt and the image's position, so a retried finalization finds it again. The part is written in the finalization transaction (`candidate_media_refs`), so sync and backup carry it like other message media. A reply with only images finalizes; one with neither text nor a stored image is `EmptyOutput`. An image the store refuses as content is left out with a warning; a store I/O failure leaves the attempt retryable; images with no store attached fail as `Internal`. When a later image or finalization fails, the images this attempt stored are deleted unless a message already links them. The run result carries the stored images as media parts, not base64. Direct and group chats share this path.

A direct chat reply's `<img>…</img>` scene tag is removed from the stored text at finalization (trimmed; closes at `</img>`, `[continue]` or `[/continue]` in any case; an unclosed tag drops the rest). The first non-blank prompt comes back as `ConversationGenerationRunResult::scene_image` when scene generation is on, its model resolves and the mode is not manual (`ask_first` for askFirst); the finalization stores it as the message's scene image follow-up in the same transaction (see Scene images). A stopped reply asks for none. Hiding the tag while streaming is a frontend job.

### Cancellation

Cancelling by durable job id records the job cancellation first and then signals the registered token. An unclaimed queued job records the turn's cancelled-before-response usage and settles turn and job at once; claimed work stays with the runner until its response evidence and cleanup settle. Completion unregisters the token. Unknown and already-terminal ids return explicit idempotent outcomes.

### Reply helper

`ReplyHelperCoordinator` ("help me reply") runs as a one-shot `CreationRun` job keyed by the request id (`one_shot_job`, shared with the scene prompt and design reference writers), so usage evidence and cancellation work like every other feature request. It is gated by `help_me_reply.enabled` before any job exists. A direct request uses the live character (definition, else description) and the effective persona (title and description, "user" and empty without one), swapped under `swap_places`; the last `history_count` visible user and assistant messages of the active branch; the `help_me_reply` model, else the default model, with temperature 0.8 and top_p 1.0 only where the model declares the parameter and the settings' output cap; the per-style prompt override (active, right purpose) or the built-in roleplay or conversational document with `{{current_draft}}`; and the runtime user entry (`runtime_reply_helper_line`, `runtime_reply_helper_input`). A group request lists every character participant as "Name (definition or description)", uses the catalog filler "participants in a group conversation" as the character description, names each transcript line's character ("Character" when unknown), never swaps places, uses the `runtime_group_reply_helper_*` texts and honours `history_count`. Streaming is a preference: the request streams only when the account has streaming on and the model does not declare it unsupported. The completion is cleaned (trim, quotes, a leading "{user}:"). A job that cannot be claimed is cancelled while still queued, and repeating a request id whose job already settled reports `AlreadySettled`.

## Companions (`companion/`)

### Companion sends

`CompanionTurnCoordinator` handles direct user sends to a companion. It detects the companion from its normalized runtime state, resolves the stored character and persona owner, reads the current authored companion config, classifies the ordered user text through the emotion classifier, applies the pure signal and turn math from `lettuce-companions`, and submits the prepared companion send, which the database commits atomically with the turn. Blank, missing or unavailable classification uses the neutral update, except that an unavailable classification from an engine that requires its model (the API's) refuses the send with `EmotionUnavailable`; cancellation stops before anything is written; an exact send replay skips classification and never reapplies state. Roleplay and group sends use the ordinary path.

For dynamic-memory companion sends the coordinator also derives the turn-effect seed from the computed transition; the database keeps it with the turn and creates the processing effect with assistant finalization. A continuation uses the zero-delta seed without a user-message owner.

### Prompt state

Context assembly reads the current authored Soul and prompting config, the character's Soul, the conversation and persona-scoped runtime state and the persona name, and renders the prompt-state block with the stored continuity episode at the source message's effective clock through the `companion_state` placeholder. The block and the scheduled-notes block render line by line from `prompt_app_companion_runtime` (bands, emotion labels, Soul lines, regulation cues, note line, truncation marker, heading); `lettuce-companions` decides which lines apply. A disabled or blank line or emotion item is left out, a disabled word fragment renders empty inside its line, and a disabled note line or block drops the scheduled-notes section. Scheduled notes come from the character's repository at the source message's effective time; the block and `has_active_scheduled_note` derive from that active set, and when the template does not use `{{scheduled_notes}}` the block goes in at depth zero. The bundled continuity entry drops its "Scheduled Background Context" sub-section with an `{{#if scheduled_notes}}` condition when there are none.

### Turn effects

After a memory cycle of a companion conversation, the terminal coordinator assigns the added and updated memory ids to each coalesced effect through its exact user and assistant source window, picks the largest-delta summary with percent rounding, wording, pluralization and a three-part cap, and settles each effect ready (a no-op success is ready) or failed with a bounded stable reason. Settlement replays idempotently. Effect-first ordering means a crash retry converges without leaving a succeeded attempt with effects still processing.

### Growth and consolidation

The terminal read also exposes up to sixteen non-blank memory items that were absent from the run's starting snapshot; that is the growth trigger and evidence. After a memory cycle that succeeds with fresh memories, `CompanionFollowUpHost` (called by the memory driver) admits and runs growth with the built-in growth prompt and, when growth applied changes, consolidation. The prompt is resolved before admission, so a missing prompt creates no job. A failed follow-up is not retried: a retry-scheduled one is cancelled, and its key is per memory run or growth job, so nothing else is blocked.

- Growth: empty and non-companion results create no job. One restart-policy `CompanionGrowth` job keyed by the memory run id freezes the successful attempt, the resolved memory profile, the current Soul revision, the character owner and the fresh-memory evidence. The claimed job renders the editable growth prompt, requires the `record_growth` tool, checkpoints the first parsed proposal and applies it through the Soul policy and repository with a stable operation id. Restart skips inference after the checkpoint and the Soul apply replays its receipt. The job settles success, cancellation, terminal rejection or a retryable failure without touching the settled chat or memory run.
- Consolidation: only a succeeded growth job that added facts can admit it, and only when the post-growth Soul has at least twelve active changeable facts. It freezes profile, authored context, Soul revision, owner and a deterministic apply id, requires `consolidate_soul`, checkpoints its first proposal and passes it unchanged through the consolidation policy.
- `resume_after_restart` runs queued growth and consolidation jobs from their stored runs, fails one the app stopped during twice and cancels one that can no longer be claimed.

### Soul writer

Soul-writer preview admission freezes the primary and optional fallback profiles, the editable prompt identity and revision, the prompt values, the normalized starting draft, the structured fallback format and the request identity before inference. Fillers and the authoring instruction render from `prompt_app_companion_runtime` at admission and are frozen; fallback instructions and tool descriptions render when a request is built, as do the growth and consolidation lines. Repeating the request id returns the stored run and its interactive job. The executor renders the prompt only at its frozen revision, appends the authoring instruction and requires the six-tool contract; it reduces and stores every native round before continuing, suppresses calls after `done`, resumes incomplete checkpoints and returns completed previews without provider I/O. No-call responses get one tools-disabled JSON/XML fallback; a failed primary target may continue on the frozen fallback profile. Cancellation, the eight-round cap, later provider failures and job settlement never promote an incomplete draft. The preview never mutates the character or its Soul.

### Soul growth edits

`clear_companion_soul_growth` (returns the count removed), `remove_companion_soul_growth` (by id) and `set_companion_soul_growth_lock` (true when the entry exists) edit the Soul the conversation grows: the character's shared Soul, or the conversation's own while the character does not share growth (`SoulOwner::for_conversation`). A write that conflicts with a concurrent growth or consolidation run is prepared again on the newer Soul, up to three times.

### Emotion model (Lettuce Thymos)

`companion_emotion_install` handles the companion emotion classifier. `HuggingFaceBrowser::companion_emotion_model` pins `Zeolit/lettuce-thymos-26m-v1` to the commit Hugging Face reports (shared `model_pin_request`, `pinned_files`). `admit_companion_emotion_install` admits one `ArtifactInstall` job below `<app folder>/models/thymos` through `ArtifactInstallCoordinator::admit_labeled` with the `Lettuce Thymos` label; progress, resume and cancellation are the job's. The job store decides whether an install is active (any queued or running job with that label, whatever revision). `active-install.json` is only a hint with the job id and pinned remote, so another request joins that job; when the hint cannot supply them the request gets `InstallInProgress` with the job to wait on, and with no active job a stale hint is discarded. Two revisions never download or complete at once.

`finish_companion_emotion_install` (busy while a job is active) records the install only after the files, label metadata and optional digest verify, replacing the record atomically, then sweeps other revisions and partials. Status and admission first reconcile: a hint whose job succeeded but was never finished is finished, one whose job ended otherwise is dropped. A succeeded job without a readable hint cannot be finished (the job store does not record the revision), so the next admission installs again. `remove_companion_emotion` sweeps the record, every revision and every partial. `try_load_companion_emotion` reports damaged, unverified or unavailable installations; API callers receive a typed model failure.

## Memory (`memory/`, `companion/companion_memory_*`)

Memory reads name the branch they act on. Generation uses its turn's branch, lorebook preparation uses the selected branch, and a queued memory batch freezes its branch at admission. The branch participates in the batch's idempotency digest, so two branches sharing a message prefix still have separate runs. Companion effect batches use the branch of each source turn and never combine sibling branches; the effect repository resolves that ownership from durable turns. Dispatch and recovery use the frozen branch and memory space after the user selects another branch.

Dynamic memory writes happen in a background cycle after turns, never inside the reply: the reply carries no memory tools. The cycle code is in `companion/` because it also settles companion turn effects; plain direct and group chats run the same pipeline with a message-window source instead of effects.

### Admission

`CompanionMemoryHostCoordinator` is the host entry point.

- `after_turn` admits and claims the cycle a finished send or continue earns, never a regenerate. Direct chats need the global `enabled` flag and a dynamic session; groups need only a dynamic session. The memory mode comes from `effective_memory`. Companion conversations admit their processing effects; plain ones admit the interval window.
- Run modes: `manual` admits nothing automatically. `ask_first` waits for the interval gate and records a pending approval without dispatch; `auto` admits one interval-sized window per run and clears any pending approval. Counting uses visible user and assistant messages on the active branch from the summary cursor.
- For companion conversations, automatic admission waits for the interval and takes the oldest ready effect prefix; a user and assistant effect stays whole across the interval boundary. The batch's idempotency key derives from its ordered effect identities and interval. Admission stores the versioned frozen branch, source identities and selection with the job in one transaction through `MemoryAdmissionStore`; duplicate discovery returns that original batch, and the queued job retains the same input through restart. A fresh job store can rebuild the same logical batch from durable processing effects. Pending effects are listed with `list_processing_for_conversation`, which filters status, conversation and invalidations before the 512-effect page limit.
- `trigger` (manual trigger and retry): the same gate, then a forced cycle over the most recent interval-sized slice of the unsummarized dialogue, or less when fewer messages exist, keeping whole effects. It never reaches back into summarized messages. It always clears the pending approval, and returns `CycleInProgress` when another cycle of the conversation is running (the check pages through every memory job of the conversation). Approval freezes the newest interval-sized suffix; older unsummarized effects stay attached for terminal settlement while only the suffix goes to inference. The group trigger keeps the oldest cursor prefix. A direct retry may freeze an explicit model profile into the job; a different resolved profile is rejected, and an opted-in default change happens only on the first successful settlement. Group retry has no model override.
- `skip` and `pending_approval_count` clear the pending flag (keeping the prompted baseline) and report the current count.

`resolve_runtime_inputs` reads live settings into the runner inputs. Model: the admission override, then `dynamic_memory_model_profile_id`, then the default model; with none the job fails visibly with `memory-model-required`, and an explicit retry can run after configuration is corrected. Prompt: the user's `dynamic_memory_prompts` override when it is an active document of the right purpose, else the local manager prompt for llama.cpp accounts or the built-in document. On llama.cpp accounts the memory call drops the creative sampler (top_k 40, zero frequency and presence penalty, repetition penalty 1.0) unless `dynamic_memory_llama_sampler_overwrite_enabled` is off. Policy, duplicate threshold and fallback format come from settings; supersession is on for companion conversations; time awareness comes from the companion clock. When a run already exists for the batch, its frozen profile, flags and fallback format win over live inputs; only conversation, space, source messages and interval must match.

### Running a cycle

`run_claimed` seeds creates with the embedding tokenizer (zero on failure) and runs the claimed-job runner, which composes these phases:

1. Admit or recover (`admit_or_recover`). The logical batch maps to one durable run in the conversation's active memory space, freezing the ordered visible messages with each one's active revision or candidate, the resolved profile, time awareness, supersession and the tool contract. `start_cycle` decay is admitted with the run, so `starting_memory` is post-decay and a recovered run never decays again. Same-job rediscovery replays the processing attempt; a replacement job recovers it into one child.
2. Summary. The editable summarizer prompt renders over the frozen window and the prior summary and requires `write_summary`; valid same-response text is accepted, else a tool-disabled retry with validation. Generated summaries require a successful tokenizer count before publishing the summary or moving the cursor; an unavailable count is a typed embedding failure, and cancellation remains cancellation. Provider usage evidence stays recorded on a counting failure. Summary, token count, context, usage and cursor commit against the memory root, and recovery replays the checkpoint without recounting or redispatching.
3. Round zero. The first-round coordinator materializes the exact message bodies, renders the memory manager prompt with the budget variables and runtime input, dispatches the frozen profile and required tool contract, and admits the single tool candidate as round zero. Rejected, empty, mixed-content, undeclared or inconsistent signed-replay outcomes do not become durable calls; cancellation settles before admission.
4. Rounds. Each admitted round reuses create preparation and the reducer with the cycle's hard-delete budget, and settles its ordered results with the memory CAS. A conflicting revision rereads current memory and prepares and reduces the same recorded calls again, for at most three settlement attempts. This preserves user edits without another inference request; cancellation is checked again on each attempt. A settled round appends its calls and results to the durable request context, stops on `done`, or dispatches and admits the next round. When a native request errors or returns no calls, a second request with tools disabled and the frozen JSON/XML instruction is parsed into the same calls, both usages aggregated; empty operations become an explicit no-change `done`. Cache-read and reasoning details of the two requests are summed only when both report them; a missing or overflowing sum stays unknown. Without `recursive_memory_loops` a cycle makes one memory request; with it, rounds continue until `done` or `recursive_memory_loop_hard_cap` (at most `MAX_DYNAMIC_MEMORY_INFERENCE_ROUNDS`), and reaching the cap or getting no tool calls ends the cycle normally.
5. Repair. Every create skipped for a missing or invalid category is re-tagged once through `retag_memory`, rendered from `prompt_app_memory_runtime`. Answered candidates become one final round of `create_memory` calls stored as `DynamicMemoryRoundKind::Repair`; unanswered ones are dropped, the last answer for a text wins, a response without a usable call still runs the structured fallback, and a request that answers nothing usable falls back to the keyword guess. A resumed job treats the repair round as terminal, an attempt that holds one is never repaired again, and a failed repair execution is logged and the cycle kept; only cancellation propagates.
6. Finish. `finish_cycle` (trim, then demote to the hot budget) commits through the memory CAS; a revision conflict re-reads and retries twice, then keeps the cycle with a warning; other storage failures settle the attempt as a recovery failure.
7. Terminal. Success feeds the starting and current snapshots to the companion effect coordinator, settles every effect, then marks the attempt succeeded. Failures and cancellation use the bounded effect summaries and failure codes; first-round and loop failures are classified through the same terminal coordinator. The job settles with complete progress on success, a bounded error on failure, or the cancellation steps; admission or terminal-settlement errors return the job to its retry queue so effects are not stranded.

Each tool result is rendered in the payload shape the model expects (`memory_tool_result`): `status`, `name`, six-digit `memoryId`, `deletedMemoryId` and `deletedText`, the `updatedMemories` list, and for skipped calls the echoed `arguments`, `repairQueued` for category skips and a readable `reason`. The `[id] text` line and every reason are `prompt_app_memory_runtime` entries (`memory_id_line`, `memory_skip_*`), which the first-round memory list uses too. Memory tool descriptions, the manager input, `none`, the JSON/XML fallbacks and the summarizer's instruction, fallback, `write_summary` texts and "No previous summary provided." come from the same document, with group variants (group runs have no `source_message_id`, and group summaries label lines `[User transcript line]:` / `[Character transcript line]:`). The manager and summarizer prompt conditions see companion time awareness (never for groups), and time-aware runs fill their date and time values.

Time-aware runs keep a known create source, fall back to the latest frozen source for an unknown or omitted id, and render transcript lines as `[message:ID] role: <time>YYYY-MM-DD HH:MM</time> content`; created memories store role, observed time and `turn` precision. Other runs clear source attribution. Companion runs expose `supersedes` and link valid active targets during reduction; direct and group runs clear the field.

Create preparation needs a claimed job with model-load, disk-read and CPU resources. It embeds candidates at the configured dimension (`embeddingDimensions`, default 768), compares only live exact-revision projections, supplies qualified duplicate evidence, and stores a projection only after the memory CAS confirms the item survived. If the embedding is unavailable the create proceeds without semantic evidence and leaves repair state, unless the engine requires its model (the API's engines do): then the cycle fails with `EmbeddingUnavailable`; cancellation stops preparation.

### Scheduling and restart

`PostTurnMemoryScheduler` coalesces cycles per conversation and branch: `enqueue` returns true when the caller must start `CompanionMemoryHostCoordinator::drive`, and turns finishing during a pass ask for exactly one more. `enqueue` and `drive` require the branch of the finished turn, so a later fork or selection cannot redirect its due window. `drive` runs `after_turn_for_branch` plus `run_claimed` per pass, logs a failed pass and continues, and stops when the conversation is gone. Group conversations use the same driver. `CompanionMemoryDispatchCoordinator` is the shared startup and post-finalization bridge: it rediscovers processing effects, claims each job with the ordinary lease lifecycle and returns the claim and cancellation handle; repeated dispatch while a conversation job is active is a no-op.

`resume_after_restart` (after `recover_after_restart`) runs each queued memory job whose conversation still admits the same window (a processing attempt of the same job resumes) and cancels the rest, which would otherwise block the next cycle. Manually triggered cycles are not resumed. A queued job the app stopped during twice (`LeaseExpired` events) is failed as `LeaseLost`, non-retryable, so a job that crashes the app cannot crash every start; its window is then held until the user runs memory by hand (a manual run uses its own key chain), its companion effects stay processing, and the frontend must say why memory paused. A window whose job failed or was cancelled is admitted again under a key chained to that job (`retry_idempotency_key`), and every input error of `run_claimed` settles the job with a retry scheduled.

### Delete-after

`DynamicMemoryDeleteAfterCoordinator::delete_after` keeps the selected anchor message and removes what follows it on the selected branch. Rewinds owed for the conversation finish first, and one that fails answers `OwedRewind`. It finds the first visible message after the anchor and asks whether any visible suffix message is also shown by another branch (`suffix_shared_with_other_branches`). When none is, the suffix is tombstoned with the branch-local policy and the owed rewind is recorded in the same transaction (`PendingSuffixRewindRepository::tombstone_suffix`); the coordinator then derives the removed ids from the durable tombstone outbox record, rewinds memory and summary from the earliest intersecting run (see lettuce-memory), invalidates the removed companion effects, admits the retained effects of the rewound suffix with a restart-stable rebuild key, and clears the record. A record a crash left behind is finished by `complete_pending` at startup and before the conversation's next memory admission; a rewind that fails is recorded on its conversation and reported without stopping startup or other chats. When one is, an ancestor or a branch forked from a suffix message at any depth shows it: the coordinator forks a new branch at the anchor through `fork_branch`, which selects it, and deletes nothing, so no rewind is owed. An anchor with nothing after it records a durable no-op operation (`record_empty_suffix`). Every outcome is idempotent by the operation key: a tombstone replay first checks the rewind receipt, a fork replay answers the recorded branch, and another request under the key is `Conflict`.

### Embeddings (Lettuce Eidos)

`embedding_models` installs embedding families. `EmbeddingModelCatalog::pin` pins the Hugging Face commit (shared `model_pin_request`, `pinned_files`); `embedding_install_plan` downloads a family below `<app folder>/models/embedding/<family>/<revision>/` as one `ArtifactInstall` job. LFS files are checked against SHA-256 while downloading; plain git files (Eidos `calibration.json`, v4 `tokenizer.json`) by size and then by git blob id (`verify_git_blob`) in `finish_embedding_install`, which also parses the calibration and removes a file that fails either check before recording the manifest. `EmbeddingModelCoordinator` loads the chosen family when installed (unset means Eidos), else any installed family, Eidos first; a completed install becomes the choice, and removing a family keeps the choice so loading falls back. `adopt_legacy_install` records the legacy `v4-model.int8.onnx` and `v4-tokenizer.json` in place and, on a device that never chose, stores v4 as the choice. Nothing downloads automatically.

The composition layer verifies an installed manifest through `lettuce-model-hub`, loads one serialized ONNX embedding runtime and runs request-scoped inference with a job cancellation token; the host schedules this CPU and model-load work on the job worker.

Re-embedding is lazy (`memory_embedding_backfill`): when retrieval needs a space, `embed_missing_memories` embeds its active memories that have no vector for the active vector-space label and dimension, which after a model or dimension switch is every memory of that space. Nothing re-embeds the whole library in the background. Imported v4 vectors stay in use while v4 is active, and old vectors become current again when the user switches back. A vector is stored only while its memory still has the embedded text (`ProjectionWrite::Superseded` otherwise), and a re-embedded memory gets its token count recounted with the embedding tokenizer (no special tokens, no cut) without a revision bump.

## Lorebook generation (`lorebook/`)

Staged draft edits, approval toggles and refinement are available during coherence review. They retain the review stage and proposals, and refinement uses the same frozen inputs and revision checks as drafting review.

All lorebook generators share one shape: preparation freezes every input into an immutable run bound to one generic creation job before any provider call; the claimed-job executor renders the frozen prompt, tries the native tool contract and uses exactly one same-profile JSON/XML fallback only when no usable native result exists; each decision, usage and provider diagnostics are checkpointed before the job settles; restart replays the checkpoint without redispatch; a changed admission replay conflicts. None of them mutates a lorebook until an explicit apply.

- Single entry: preparation resolves the direct conversation's character and persona, reads the selected branch messages, memory, summary and target lorebook, and freezes the chronological message, memory, relative-time, existing-entry and `(none)` formatting. Missing or foreign selected message and memory ids fail closed. Selected memory lines are numbered contiguously over non-blank memories.
- Keywords: freezes the title, content, existing keywords and direction with the active keyword prompt and profile, and runs the required native contract plus one fallback.
- Final instructions, fallbacks, tool descriptions and fillers (`(none)`, `[empty message]`, numbered lines, existing-entry lines) render from `prompt_app_lorebook_runtime`. Fillers are frozen at admission together with the filler that marked an absent input (`none_marker`), so later catalog edits cannot change a run's source gates; instructions, fallbacks and tool texts are read when a request is built.
- Entry and keyword executions record each dispatch in the job usage ledger. The shared helper tells evidence-storage failure apart from provider failure: on evidence failure they stop without a false failed-native checkpoint or a fallback; provider failures keep the fallback policy. Primary and fallback ids and usage stay separate, and replay adds no dispatch.

### Staged lorebook generator

The staged generator builds a whole lorebook from source documents in stages: plan an outline, review it, draft entries in batches, refine, check coherence, commit. The project lives on one stable row changed by CAS, with each stage's frozen inputs and attempts stored in immutable run documents.

1. Sources. `prepare_staged_lorebook_documents` reads ready `SourceDocument` assets through protected media handles, enforces per-source and total byte limits, verifies content hashes and prepares ordered, bounded text and PDF excerpts; only the extracted snapshots are kept. `with_sources` prepares pasted text or UTF-8 TXT and MD bytes, truncating before job creation.
2. Settings. Explicit overrides, persisted generator settings and packaged prompt ids combine; the model's lorebook-generator slot uses the operation parameter layer; unset temperature and top_p are 0.3 and 1.0, unset output tokens the generator setting (default 4096); other unset fields inherit the model; reasoning is disabled (an explicit Disabled mode in prompt conditions counts as off). `admit_configured` loads settings, the model, account and planner prompt, resolves the profile, applies target-count defaults and bounds and admits the planner; missing references and incompatible profiles fail before job creation. Explicit project overrides persist, and later selection uses operation override, project override, then live settings and defaults.
3. Plan. The planner renders the brief, decimal target count, excerpts, final instruction and required tool, makes one native request, accepts only typed tool calls, checkpoints calls, usage and diagnostics, then moves the project to outline review; the planner job succeeds while the project waits. An explicit retry admits a new job only after the previous one failed, keeping project, sources, profile and prompt.
4. Review. Pre-approval outline edits are project CAS operations that keep planner evidence. Approval creates the ordered pending drafts and enters drafting without dispatching writers.
5. Draft. `start_configured_batch` persists the profile, prompt identity and revision and operation overrides atomically with the batch start, then selects the first three pending or failed drafts in outline order, marks them drafting and creates deterministic writer runs and jobs (identity from the stable plan id and batch revision, replay with the frozen start time). Partial admission resumes from that checkpoint without re-resolving settings, including entries that have no job yet, and a low-level caller cannot replace a frozen batch profile; a batch without this checkpoint uses its resolved profile. The writer renders the full outline, proposed keys and relevant excerpts with the final instruction and one required native tool; its checkpoint is durable before the draft CAS. A terminal writer failure marks its draft failed; a transient retry keeps it in the batch; retrying failed drafts admits new jobs while completed drafts stay; a late failure from an older batch closes only its job. Writer batches validate prompt and text modalities before changing the project.
6. Edit, refine, coherence. Draft edits and approval toggles are project CAS operations. Refine freezes the draft, trimmed feedback, render values, profile and prompt, checkpoints one attempt and commits the revised draft plus history; a failed refine keeps the reviewed draft. Coherence freezes the drafted-entry rendering, profile, prompt revision, project revision and job, checkpoints one attempt, submits proposals, and applying only the accepted change ids returns the project to drafts-ready.
7. Commit. The final commit takes a new destination and name or an existing destination revision and delegates one atomic apply to the creation repository; the project keeps the receipt for exact retries.

Every admission also stores the full validated prompt document, and first inference uses that frozen document, so prompt edits affect only newly admitted work. Planner, refine and coherence admission replay use their saved inputs even after settings or model changes, and changed feedback, ownership, time, safety or overrides conflict. Checkpoint replay checks job ownership and cancellation but not the live prompt revision. Writer and coherence render values are rendered at admission and stored with their `(none)` filler; the planner's excerpts, final instructions and tool descriptions render when a request is built. Project cancellation cancels queued jobs and requests cancellation of claimed ones; all executors check the project before and after inference, dispatch settlement recognizes a cancellation racing a provider completion, and a late response after durable cancellation is discarded (the host can also signal the job handle to abort the transport). Every actual dispatch, including invalid responses and cancellation during inference, is recorded in the job usage ledger before response handling; checkpoint replay creates no second record.

## Creation helper (`creation/`)

The creation helper is an agent loop that edits a draft character, persona or lorebook through tools until the user confirms.

- Admission records one user turn and its first attempt in one transaction against the exact workflow revision and base proposal; exact replay returns the pair, and changed identity, stale state or a job collision rolls back.
- Dispatch is bound to the attempt's claimed job and a BLAKE3 fingerprint of the resolved profile; a stale caller, reused job or profile drift is rejected before any request.
- Each request is built from `prompt_app_creation_helper`'s seven system entries (role, intake, creative principles, output contract, tool use, examples, `<current_draft>`) with `{{target_label}}` and the `DRAFT (...)` view from `prompt_app_creation_runtime`, then every earlier successful turn (its message and the trimmed visible text of its attempt; reasoning is not replayed), then the current message; in-chat entries go in at their depth. On llama.cpp every entry is trimmed and joined into one leading system message, because chat templates such as Gemma reject a second system message; other providers keep one message per entry. Lorebook drafts list their entries with ids; descriptions are never shown. The oldest turns are dropped to stay under the 512-message context limit with room for eight rounds. Tool arguments are kept verbatim.
- Rounds continue until a response has no tool calls (previews and confirmation requests do not end the turn). After eight rounds, or once the attempt reaches the 64-call cap (a round keeps only the calls that fit), the attempt settles with the proposal so far. A request that cannot be built fails the attempt. A text-only response stops without inventing a proposal; tool-driven completion appends exactly one planned proposal.
- Rounds are admitted as immutable creation rounds with text, reasoning, calls, usage, finish metadata, request identity and replay evidence. Recovery rebuilds the proposal and the call and result continuation without redispatching completed rounds; interrupted recovery settles the parent as interrupted and creates an empty child with the same base and profile, a new planned proposal and a new job. Successful continuation commits the reduced proposal, workflow advance and attempt success in one transaction. Each dispatch is recorded in the job usage ledger before validation, and evidence failure stops the run without being classified as a provider failure.
- Tool results have the shape `{success, message, error?, ...}` rendered from `prompt_app_creation_runtime` (`Name set to 'X'`, `Scene added` with `scene_id`, `entry written` or `entry updated` with id, title and content, argument errors such as `SET_NAME requires args: name=<text>`, preview and confirmation with `action`, the model's message or a default text, and the draft at that call). The `entry` and `draft` values use the rewrite's draft shape, and the draft is left out when the result would pass the 1 MiB limit. A call to an undeclared tool is recorded as `UndeclaredTool` and answered `{success: false, error: "unknown tool: NAME"}`. Rewrite-only failures (blank text, limits, unknown or duplicate ids, a missing entry title, a tool unavailable for the draft) have their own texts. An error replaying a stored round, other than storage, fails the attempt.
- Apply: confirmed new and existing personas, characters and lorebooks each go through one use case that delegates to the creation repository's atomic apply (entity plus receipt); callers never coordinate the domain write and the receipt themselves.

## Images (`image/`)

- `ImageGenerationCoordinator` runs image requests as `ImageGenerate` jobs with a durable generation record; `image_providers` composes `RemoteImageProviders` with a `BulkHttpClient` built from the TLS policy, and local models go to the stable-diffusion.cpp engine. `playground_history` lists the playground history newest first (30 by default, 1 to 200, paged by creation time) and `delete_playground_history` removes an entry and, when asked, its image assets unless the library keeps them or something else uses them.
- `image_feature_models` decides which model a feature uses: the settings choice when it suits the feature, else its fallback (the default model or the first suitable model in settings order).
- Local stable-diffusion.cpp (`local_diffusion`, `local_diffusion_install`): engine builds, catalog models and the upscaler install as pinned artifact installs, and a catalog model is registered when its download finishes. Placement and auto-fit see discrete GPUs and accelerators, plus the AMD integrated GPU of a unified-memory machine whose only GPUs are integrated (an AMD APU such as a Ryzen AI handheld, detected with llama.cpp's `is_unified_memory` test). That iGPU is budgeted from the memory it reports, which follows the user's carve-out; the fit formulas are unchanged. Intel and other integrated GPUs, and an AMD iGPU next to a discrete GPU, stay excluded. Reading the installed list removes `sdcpp:<profile>:<variant>` models whose variant is not installed; an installed variant keeps its row so registration adopts its settings.

### Scene images

`scene_generation_request` builds the image request for a direct chat message:

- The scene model comes from `image_feature_model(Scene)`; the character and persona are read live, and the persona is the conversation's effective one.
- A local diffusion model gets the trimmed scene prompt and the character and persona recommendation LoRAs (`scene_loras`), each kept when it has no keywords or one appears in the prompt.
- A remote model gets, in order, the character's design references (else the original avatar), one chat background (the conversation's own, none when hidden, else the selected or default scene's, else the character's) and the persona's design references (else the avatar). The prompt is the sections rendered from the `scene_image_*` catalog entries, bounded at 64 KiB. More than 16 references drop persona references first. Unreadable references are skipped, and a subject whose references are all unreadable falls back to its avatar.
- The size is the model's own, else `scene_default_size`, else 1024x1024, and is always sent.
- The request is an `ImageGenerate` job with source `Scene`, queued by the follow-up and claimed by the job runner's `ImageGenerateHandler` (one handler for every image job, so `job_cancel` reaches a scene image and nothing else claims the job); the API context carries the image provider (`AppImageProviders` in production).
- `attach_scene_image` adds the first generated image to the render target captured by its request. A generated candidate's latest edit retains previous media; switching candidates preserves the image in that candidate's history, and selecting it renders that edit. A native starter revision retains its own history when a later user edit becomes active. The attachment operation is derived from the existing request identity and target, so replay appends each image once.

The follow-up (`lettuce_conversations::SceneFollowUp`, table `scene_image_follow_ups`) holds a checked generated-candidate or native-starter-revision target, prompt, mode and state with its current attempt and image request. Finalization writes each generated candidate's tag in the same transaction; regeneration leaves older candidates' follow-ups intact. `SceneFollowUps` drives compare-and-set transitions and recovers each unfinished row independently. A missing image retries up to three provider attempts; missing media storage fails with `MediaUnavailable`, an interrupted job with `Interrupted`, and cancellation dismisses the follow-up. Automatic startup uses the completed turn's candidate identities. Manual prompt and image commands require the existing `client_operation_id`: the same key and request replay the original job, and a different request under that key conflicts. Manual admission captures its render target; the prompt job also stores the target's rendered recent-message context before queuing. Generic job details and operation receipts are committed with job admission. Follow-ups, details and receipts are backed up; sync leaves them device-local.

### Scene prompts and design references

`ScenePromptWriter` turns a direct chat message into one image prompt with the scene writer model (`scene_writer_model`, vision required unless the scene image model is local). Its context is the message and the two positions before it in the loaded window (latest 120 messages plus older pinned ones, any visibility), user, assistant and scene lines only, with `{{image:…}}` spans removed. The active `prompt_app_scene_prompt_writer` document renders with its placeholder values and condition facts; writer-side text (scene request, reference notes, hints, background notes, role labels) is `scene_writer_*` runtime text. Reference hints count the stored design images and condition flags follow the images that can be read. A remote scene model gets those images as multimodal user messages; a local one gets the subjects' LoRA bindings and no images. Conditional and interval entries are placed by relative message count, in-chat entries at `depth` from the end, and a condensing template merges every non-image entry into one system message. Image tokens left in a system or assistant entry are removed, blank messages are not sent (though they count for placement), `{{char}}`-style names inside descriptions are substituted by the shared renderer, and `{{image[avatar]}}` / `{{image[references]}}` render empty. It runs as a non-streaming one-shot job with `SCENE_WRITER_DEFAULTS` over the model's scene writer slot, and usage is recorded before the answer is cleaned, also when the answer is empty.

`DesignReferenceWriter` drafts design notes for a character or persona: the scene writer model (vision required; scene generation need not be on) reads the avatar and reference images the caller already stored (at least one) and renders the active `prompt_app_design_reference` document, relative entries first, then the rest, each in template order; condensing merges non-image entries. The subject name defaults to `design_reference_unnamed_subject`. It runs as a one-shot job with `SCENE_DESIGN_REFERENCE_DEFAULTS` over the scene writer slot, streams when asked and possible, records usage, and cleans the answer (quotes, code fences, blank lines). `feature_prompt_entries` holds the rendering it shares with the scene prompt writer.

### Avatars

`avatar_image_prompt` reads the active `prompt_app_avatar_generation` or `prompt_app_avatar_edit` document: enabled non-blank entries in order whose `hasSubjectDescription` or `hasCurrentDescription` conditions hold (other conditions pass), joined by blank lines, then the nine placeholders replaced in order with trimmed values; nothing else is substituted. With no entry selected, the bundled seed's enabled entries stand in. Local stable-diffusion.cpp models get the request as typed.

`AvatarGradients::gradient(media, asset, force)` samples about 100 pixels, quantizes them by median cut to 8 colors and picks a dark muted base, a muted companion and a dark vibrant accent, with CSS and text colors; it is checked against the original functions on 400 sample sets (`tests/fixtures/legacy_avatar_gradients.tsv`). The caller picks the image; the round image falls back to the square avatar until a round asset exists. Results are cached per process by content hash. A single-color image spans 0% to 100%, and GIF avatars decode.

## Speech (`speech/`)

- Transcription: `SpeechTranscribe` jobs are admitted idempotently and bound to one immutable audio and model request, claimed through the generic lifecycle, then decode managed audio, build the prompt from the ASR learning library, run Whisper, apply corrections and settle durably. Results replay after reopen; cancellation reaches the runtime token; unavailable audio, storage, models or runtimes retry and malformed inputs fail. `AppBackend` owns one process-lifetime `WhisperCppRuntime` so verified contexts are reused, and `run_speech_transcription` supplies the real learning and Whisper adapters.
- Whisper models: the remote catalog resolves the repository head to an immutable commit (shared `model_pin_request`, `parse_pin_listing`; Whisper, Kokoro, artifact-install and GGUF-header downloads build URLs with `pinned_resolve_url` / `resolve_url`) and exposes only entries with coherent LFS size and SHA-256. Downloads are durable artifact-install jobs with byte progress, resume at the requested offset (restarting when a server returns the whole object), SHA-256 verification, atomic install and a BLAKE3 manifest afterwards; a crash between rename and manifest recovers from the verified file, cancellation works until the irreversible install stage, and completed jobs replay without network access or a public native path. `WhisperModelCoordinator` scans the retained legacy model directory, records verified manifests, resolves the first-filename default or an explicit id and revalidates size and BLAKE3 before building the request; the runtime repeats that verification before loading native code; removal validates ownership, clears cached contexts before deleting bytes and then deletes the exact manifest, and a missing retry is a no-op.
- ASR learning: `AsrLearningTransferCoordinator` exports the four record classes as one bounded versioned document; import validates every record and link, verifies each managed audio asset against its content and provenance, remaps voice links and commits one batch.
- TTS configuration: remote credentials are created only in the native secret store under `AudioApiKey` ownership, with the reference stored through the speech repository; key rotation uses secret generation CAS, provider and voice updates revision CAS, and the provider kind cannot change. Deleting a provider validates its revision, removes its voice graph and deletes the matching secret generation; a secret-store failure after metadata deletion returns an opaque retry receipt. Kokoro takes no credentials. Remote transports use the host's TLS policy. ElevenLabs and hosted Fish voice refresh loads only the provider's secret, rejects partial responses and replaces the provider's voice cache after a complete fetch.
- Verification: ElevenLabs, hosted Fish and Gemini load the provider and its exact secret scope before the typed verification call; a credential rejection returns `false`, other failures stay distinct errors. Gemini also needs project and location, Fish Speech supports authenticated and unauthenticated servers, and OpenAI-compatible verification performs a real models probe.
- Voice design: ElevenLabs only. It freezes the provider snapshot, validates sample and description, resolves the scoped key, passes cancellation to the runtime and sends decoded preview bytes to the media sink as temporary assets with an admitted expiry (no extra job table). Each result keeps the generated voice id, duration, detected MP3 MIME, hash, size and asset identity; provider base64 and plaintext credentials never cross that boundary. Creating a voice from a preview admits a non-retrying `speech_voice_create` job. Its result contains the provider voice id for the separate user-voice save; running interruptions have a typed outcome-unknown result, while queued restart cancels without sending.
- Synthesis: `SpeechSynthesize` jobs persist provider, text, voice, prompt and output policy before execution, load the exact provider secret when needed and admit returned bytes under a deterministic asset id (temporary for previews, persistent for chat audio). Cancellation is checked before secret access, before dispatch and after the response, so late audio is not stored. Transient failures requeue the same request; invalid inputs and audio fail terminally; results replay after reopen. The TTS runtime routes remote kinds through the five HTTP adapters and Kokoro through native synthesis. `tts_audio_cache` reuses a finished synthesis of the same text and drops stored audio nothing else keeps.
- Kokoro: the asset inventory is built once from a host-resolved managed root and reports model, config and tokenizer presence and installed voices without native paths; missing assets are a usable status, while unsupported variants, empty files, symlinks and inspection races fail. The voice catalog reads the same pinned repository revision, accepts only bounded `voices/<safe-id>.bin` entries with coherent LFS size and SHA-256, sorts and deduplicates ids and merges installed flags, without downloading or exposing paths. Model bundles install as one durable job for four pinned files through the ranged artifact client; voices install as one stable-id job for a single voice or a batch (the starter pack), each verified before atomic commit, with an immutable descriptor sidecar so persisted selections resolve offline after restart (sidecar-free or invalid retained binaries stay untouched and unavailable to that path). Cancellation is possible until the first verified file commit; after it the job finishes or retries the rest under its irreversible stage. Removal accepts only a pinned identity, verifies bytes before deleting and keeps a variant's shared JSON assets; a later install gets a successor job. Phonemization runs only after the whole bundle reverifies and uses the purpose-specific eSpeak capability. Voice blending resolves each voice id to one pinned descriptor and hands only bounded voice material to the speech boundary. Native synthesis revalidates the bundle, runs cancellation-aware ONNX chunk inference into a bounded WAV off the async worker, honours the model override, single or camel-case JSON blend document and positive speed from the voice prompt, and merges the optional `lexicon.json` (flat or global-plus-language) for the primary voice before eSpeak. Missing assets and libraries retry; malformed requests and changed artifacts fail before ingest.
- Downloads: a cancelled or permanently failed download deletes its partial file; a retried one resumes. Partial names start with a hash of their target, so preparing a download deletes that file's partials from older revisions, and nothing outside the managed `downloads` and `.downloads` folders is touched. A partial holding every byte is verified without a request, and one that fails verification is deleted. Whisper and Kokoro check only presence at their installed size at use time; contents are hashed once at install. A Whisper model installed from an older upstream revision is used as installed; one whose file is gone or resized is dropped and downloaded again. A Whisper model imported from a retained legacy folder can be removed: its file is deleted when inside the managed folder, else only the record goes.

## Models (`models/`)

- `HuggingFaceBrowser` searches models, lists an author's models, overview and avatars (cached for the browser's lifetime, six lookups at a time), a repository's files and README, signed in with the saved token, with a 30 s timeout and no retry. `save_token` stores a token only after whoami accepts it; `auth_status` reports missing, invalid (refused) or valid, and unknown while Hugging Face is unreachable or answers with another error; `clear_token` removes it. A token the store cannot read is an error, not an anonymous request. Requests are built and responses parsed in `lettuce-model-hub`'s `hugging_face.rs` and sent through `lettuce-network`; `scripts/check-hugging-face-paths.sh` (run by `scripts/check-architecture.sh`) refuses a Hugging Face host or API path in a string literal of any other production Rust source (only `#[cfg(test)]` modules and test files are skipped) and a Hugging Face host anywhere in the frontend source outside the generated bindings.
- Runnability: `runnability` and `recommendation` read the smallest file's GGUF header (512 KiB, then 10 MiB when essentials are missing) through `GgufHeaderSource` (`ArtifactDownloadClient` reads only the requested prefix) at the revision the model page listed the files at (`HfModelInfo::revision`, else `main`), give up after the 30 s browse budget for both reads together as legacy's client did, cache a header per repository, revision and file for the life of the process, and say whether they could. `local_file_runnability` scores a downloaded file with its projector and GPU draft model (the DFlash drafter when DFlash is on, else the MTP one). Hardware comes from `local_runnability_hardware()` (nothing on mobile) or, for an Ollama account, `sprout_runnability_hardware`, which asks the account's active Sprout probe for the remote machine's memory.
- GGUF downloads: `gguf_install_plan` pins a model file with its optional projector and MTP draft model to the requested (else the current) repository revision as one `ArtifactInstall` plan below `llm_models_root` (`DeviceSettings.llm_models_dir`, else `<app folder>/models/gguf`), downloads signed in with the saved token. Image models live in `image` below a chosen models folder, else `<app folder>/models/image` (`image_models_root`, `image_model_roots`). `register_downloaded_gguf` adds the llama.cpp model (through the model-file settings mapping; the first model becomes the default), or returns the llama.cpp model already using the file. `gguf_library` lists (nested folders included, flagging DFlash drafters by `dflash.block_size`, desktop only), finds the models pointing at a file (`ModelFileReferences`), deletes and adopts model files, and moves the whole folder: files are copied, every stored model path inside it (llama.cpp and stable-diffusion.cpp, one transaction) is rewired, then the originals go.
- Image bundles: `bundle_role_search`, `bundle_files` (pinned files; GGUF text encoders checked by header), `bundle_install` (engine estimate gate, every asset re-checked, manifest written, one pinned install below `<image root>/huggingface/<author>/<repo>/<revision>`) and `bundle_retry_downloads`; `finish_hf_bundle` registers the model through `register_hf_bundle_model` (existing models keep name, settings and bindings), with `retry_hf_bundle_registration`, `downloaded_image_models` and `component_library`. Callers pass the checked assets back and they are re-verified.
- CivitAI: `CivitaiBrowser` searches (up to five fetches per page) and opens models with the saved token and validates, saves and clears the token; `civitai_lora_install_plan` sizes the file with a one-byte ranged request (the install checks exact size and the listed SHA-256), and `record_civitai_lora` stores trained words and base model afterwards. The Pure mode level is passed in.
- `artifact_install` installs a set of pinned files (Hugging Face or HTTPS) as one resumable, verified `ArtifactInstall` job below one root.
- ONNX Runtime: `OnnxRuntimeInstaller::ensure` makes the runtime available before embeddings, the emotion classifier or Kokoro load: the `ORT_DYLIB_PATH` override, then a bundled library in the host's resource folder, then an earlier download in `<app folder>/onnxruntime`, then a fresh download of the official ONNX Runtime 1.22.0 archive as an `ArtifactInstall` job below `<app folder>/downloads/onnxruntime` (progress through `OnnxRuntimeInstallEvent`, cancellation through the caller's token). Unpacking is the job's install stage (`ArtifactInstallCoordinator::run_then`), so the job succeeds only with a usable runtime; the archive is deleted once unpacked or after an unpack failure, and macOS falls back from the architecture archive to universal2. Unpacking and the disk lookup (with macOS `lipo`, `otool`, `codesign`) run on blocking threads, calls are serialized per process, and once the process committed its runtime `ensure` and `installed` return it without the disk. `OnnxRuntimeReady` hands out the embeddings and emotion link; `initialize` commits the process's single ONNX Runtime environment and returns the `OnnxRuntimeCommitted` evidence Kokoro sessions require. `KokoroTtsRuntime` gets that evidence from a `KokoroOnnxRuntimeProvider` before any Kokoro work: `ProcessOnnxRuntime` (wired by `AppBackend::tts_runtime` with the host's `OnnxRuntimePaths`) reuses a committed runtime, else runs `ensure` and `initialize` (the linked runtime on Android and iOS). Only this crate creates the evidence (`unsafe` `after_process_commit`). The install stage renews the job lease, and a runtime unpacked before the job record failed is still returned, with the job closed best effort. Android and iOS never download. The archives have no published checksum, so the download is checked by the size the server reports.

## Files (`files/`)

- Characters (`character_files(media_store)`): `read` parses text and `read_file(filename, bytes)` reads a `.png` card from its `ccv3` or `chara` chunk with the picture as avatar. `import` stores avatar, background and scene background data URLs as media assets first (a failure only leaves that image off) and then writes bundled lorebooks, the card's embedded `character_book` as a new lorebook bound last (keys plus secondary keys, `constant` always active, `insertion_order` as order), the character, its bindings and scheduled notes in one transaction. Card tags are split on commas, trimmed and blanks dropped; blank sources and non-string localized creator notes are skipped; a remote background is skipped; images are stored as given. `export(character_id, format)` writes UEC, Chara Card V3 or V2 with avatar, background and scene backgrounds inlined as data URLs; an unreadable image is left out.
- Personas (`persona_files(media_store)`): reads a persona UEC or the pre-UEC package, imports it (avatar stored first and left off if it cannot be, the file's lorebooks bound in order when they exist here, default persona when the file says so) with persona, bindings and default change in one transaction, and exports a v2 persona UEC with avatar inlined and enabled lorebooks in binding order. A missing description imports as empty; lorebook ids that do not exist are not stored.
- Chats (`chat_files()`): `import_direct(raw, file_stem, character_id, now)` imports a SillyTavern JSONL transcript as a new chat with the chosen character (`TARGET_CHARACTER_REQUIRED` without one), titled by the header's character name, else the file stem, else `Imported Chat`. Empty messages are skipped, swipes become variants with `swipe_id` (else the first) selected, user and assistant lines keep their time as effective time, and the conversation is written in one transaction through the history writer. A companion character gets the chat as its next continuity episode. `export(conversation_id, now)` writes the active branch as JSONL: shown content, an assistant's candidates as swipes when there are two or more (an edited message shows its edit first), speakers by current character names, the user as the persona title or `User`, and a `{group: true}` header plus title for groups; tombstoned messages are left out. `import_group(raw, participants, now)` maps every named speaker to an existing character (`UNRESOLVED_PARTICIPANTS:<names>`, or `GROUP_CHAT_IMPORT_REQUIRES_CHARACTER_MAPPING` without any mapping; archived characters count as unresolved), creates a group with conversation mode, LLM speaker selection and manual memory named by the header or `Imported Group Chat`, and writes its chat with each assistant line authored by its speaker. All checks run before the group is created, and a transcript whose speakers map to one character becomes a direct chat.
- Prompts (`prompt_files()`): imports a USC card or SillyTavern preset as a new user prompt (the host passes localized names for an unnamed entry and preset) and exports a template as `system_prompts_<name>_<date>.usc` or `.json`; built-in entries export under their catalog keys.
- Chat templates (`chat_template_files()`): adds a USC or JSON chat template as the character's last starter, leaving off a scene of another character, a prompt that is missing or not the character's chat purpose, and missing or archived lorebooks; exports a starter as `chat_template_<name>_<date>.usc` or `.json`.
- Models (`model_files()`): imports a model file as a new chat model on the account with the file's provider id and label, else the provider's only account (`NoProviderAccount` otherwise), returning settings that were out of range or unknown; exports as `model_<display name>_<date>.json` or `.usc`. Every imported model is a chat model.
- Lorebooks (`lorebook_files()`): imports a World Info file as a new `LegacyV1` lorebook (entries in file order, literal matching) and exports as World Info or a USC card, entries in order. The command layer names a nameless file after its filename.

## Legacy import (`legacy/`)

The legacy import reads the old app's database and storage read-only and writes the rewrite's data through the same repositories as live use. It is always a replacement: `LegacyRestoreCoordinator` imports into a new database file and switches to it only when every stage completed.

1. Inventory. `preflight_legacy_database` exposes the read-only SQLite inventory; `read_legacy_database_inventory` turns a legacy app data directory into the same `LegacyBackupInventory` a legacy backup archive decodes to: the database documents plus every regular file under `lettuce/{images,avatars,attachments,sessions}` and `generated_images`, in archive order and within the archive entry, object and total limits. Symbolic links are never followed and names that cannot form a safe archive path are left out, so the walk cannot leave the legacy roots.
2. Plan. `plan_legacy_database_import` plans the inventory through the shared legacy backup planner into one `LegacyImportPlan`, so a live database and a backup produce the same plan. ASR rows and voice audio come from the database tables (the backup's ASR document has no row ids or voice examples) and merge into the media plan under the same limit. The `plan_legacy_*` methods expose the persona, lorebook, provider and model (credentials only as key presence and header names), prompt and media plans. `plan_legacy_media` resolves persona and lorebook references below an explicit storage root plus ASR voice audio (which may be an external file the user picked), hashing bounded regular files without copying them.
3. Admission. `LegacyImportAdmissionCoordinator` fingerprints the inventory and every plan, derives the closed source id set, and admits it through the transfer repository port; SQLite returns sealed account, profile, prompt, secret-reference, graph and media mappings, so retries use the same destination ids. The deterministic legacy llama.cpp account joins the same assignments. The coordinator allocates no ids and touches no files or secrets.
4. Secrets. The provider-secret coordinator requires the live source to match every sealed assignment, writes each value only through `SecretStore` under its assigned reference and owner, and records non-secret progress per value. Retry verifies purpose, generation and the exact stored value; a correct value without a receipt is a recoverable crash; a changed, missing or foreign value stops without overwrite. App-wide tokens (Hugging Face, CivitAI) go to their fixed references, and a token already set on this install is kept.
5. Media. `LegacyMediaImportCoordinator` reopens only confined regular files under the read-only root, rejects symlinks and path drift, rechecks length and BLAKE3, catalogs each file under its assigned asset id and records completion after the blob is ready; partial progress resumes. Shared bytes deduplicate to one blob with distinct asset ids. `execute_from_source` takes the bytes a planned source retained instead; candidates the source does not hold are read from the root. Voice examples become persistent `OtherAudio` assets.
6. Graph, providers and ASR. The graph coordinator recomputes the plan fingerprint and asks SQLite to create lorebooks, personas, bindings and the default owner once every media receipt verifies. The provider/model coordinator verifies every assigned secret reference against its receipt before SQLite writes accounts, models and prompts (preserving entry order and execution flags and mapping the app default). The ASR coordinator writes all learning records in one transaction, binding examples only to completed audio; its receipt replays without overwriting live data, and graph import can proceed before voice audio is available.
7. Stages. The characters stage (`execute_database_import`) requires the plan's source fingerprint and runs after the persona and lorebook, media and provider/prompt steps; groups need the characters stage and group conversations the groups stage. Characters, groups, audio (each legacy audio API key stored under its deterministic reference first; a retry compares instead of rewriting), settings, direct and group conversations, usage records, creation helper sessions, images (LoRA library and playground history) and local generation metrics, each through its `legacy_*_importer`. `complete_legacy_import` marks the run completed only once every stage in `LegacyImportStage::ALL` has committed.

### Conversations

`legacy_direct_conversation_importer` turns each direct session into a finished conversation. Launch snapshots come from `ConversationLaunchPlanner::prepare_direct` against the imported character, persona, scene and default model; conversation, message, candidate, memory, companion note and audio ids derive from legacy ids within the run's `LegacyIdScope`. A replay returns the committed stage receipt before any planning, so sources changed after the stage cannot block it.

- Each assistant variant becomes a candidate of its own succeeded turn (send or continue for the first, regenerate for the rest) with a usage event keeping the prompt and completion tokens when both exist; the selected variant stays active, or without a selection the variant matching the message content. Without a parent message or chat model the variants become ordered revisions. Candidates carry the launch model snapshot; the legacy message model is kept only in usage. Message reasoning goes to the active variant. Speed stats (`first_token_ms`, `tokens_per_second`, `mtp_stats`) become message-only `llm_generation_metrics` rows under the candidate's attempt with the runtime's keys (`ttftMs`, `decodeTokensPerSecond`, `mtpStats`, plus prompt, completion and total tokens when known); the shown variant falls back to the message row's stats, non-JSON `mtp_stats` is left out, and replies imported as revisions keep no stats (a warning counts them).
- The session's selected scene is the conversation's scene whether or not the chat opens with it; an opening scene row becomes a scene message with its origin, template rows stay plain and hidden system rows stay hidden. A blank title falls back to the character name; the launch key derives from the session id. Branch sessions stay separate conversations.
- Session settings become current conversation settings: author note, prompt override (imported only when available with the conversation's purpose; a session imported as a companion chat imports none, while a session whose own mode alone was companion runs as a direct chat and keeps it), lorebook override (an empty list disables lorebooks), model settings, background and, for groups, a speaker selection that differs from the profile. A template that imports becomes the current override, so the imported chat keeps its prompt; a null or unimported template imports no override, so turns follow the live character.
- Memory: memories that fit the rewrite's item become the conversation's space with per-session ids and deterministic short ids; stored embeddings of 64 to 768 dimensions become ready projections under their legacy source version. Memory texts no embedding carries become memories of their own with manual defaults and no token count, but only where the old app showed them: always on manual memory, on dynamic memory only while the chat had no embeddings (dynamic means the global switch and the character's memory type for direct and companion chats, the session's type for groups). The summary covers the visible user and assistant messages up to the legacy summary cursor, taken from the newest memory cycle in `memoryToolEvents` that still advanced it (not reverted, not an error or user edit, anchored in this conversation; the pool carrier reads the pool's events); later messages stay unsummarized. Memories in an incompatible shape stay in sealed evidence.
- Companions: a direct session of a companion character becomes a companion conversation bound to the character's shared pool, which takes the legacy shared companion memory when one exists and otherwise the memories of the character's most recently updated session that has any; ready embeddings land with the conversation that creates the pool and the summary with the carrier. Session state comes from the legacy `companionState` JSON (clamped into range, launch defaults when unreadable) with the pool relationship of the session's raw persona key; every conversation of one character and launch persona shares the latest conversation's relationship. Continuity episodes are placed in one chain per character and launch persona by start time, renumbering indexes and links; unrecorded sessions start at creation and end where the next begins. Conversations are written in episode order. Legacy Soul facts that form an exact snapshot replace the imported character's authored facts (source memory ids mapped), and scheduled notes are written in the same stage (rejected notes, such as blank content, are left out). `companionState.preferences` (time awareness, off when absent, and its frozen or ticking override; an override missing its anchor runs on real time) becomes the conversation's `companion_clock`; a companion session without saved state takes the character's `time_awareness`. A session's own background becomes the conversation background.
- Several companion conversations feeding one pool each summarize their own dialogue through `summary_cursor`, while the pool keeps one cumulative summary.

`legacy_group_conversation_importer` does the same for group sessions after the groups stage. It launches from the imported group profile patched with the session's chat mode, memory policy, character-lorebook switch, member model overrides and own starting scene (a group-owned scene with session-derived ids, snapshotted only; `GroupLaunchOverrides`), passes the session lorebooks only when overridden, and rewrites the cast to the session's members: planned member snapshots are reused, members the profile no longer lists are snapshotted, and speakers whose character is gone become disabled, muted "Unknown" members so their messages keep an author. An all-muted cast unmutes one member, a message's author follows its active candidate, and members without a model inherit the group model or the first member override. Group sessions whose group profile is gone are recorded as `MissingGroup` skips.

`legacy_creation_importer` seeds a workflow with its initial proposal for every creation session whose untouched active draft fits the rewrite's draft; sessions with chat, tool history, draft history or images stay in sealed evidence.

### Legacy restore

`LegacyRestoreCoordinator` loads a version-1 backup (decoded, planned, staged and admitted) or a live legacy data directory (planned in place) into a new database file, running the whole chain in stage order: admission against the derived source counts, media from the planned source's retained bytes, provider secrets, the authored graph, ASR learning, providers, models and prompts, then every stage. Only a completed run carries device-local state from the previous database, records the backup admission and switches the active database; the previous file is never deleted. Each restore stages into its own `<workspace>/<restore_id>` directory. Provider secrets get fresh references at admission and audio keys references derived from the source and run, so a replacement never shares a secret record with the database it replaces, and a failed attempt deletes the secrets it wrote.

Version-2 ASR JSON import validates every identity, value, timestamp and link before opening audio; relative voice paths are confined to the document's directory, absolute paths are allowed (the old file-picker flow), symlinks and non-files are rejected, each distinct file is ingested once as library audio, and the converted graph uses the same atomic learning import. Source JSON and audio are never modified.

## Backup and restore (`backup/`)

### Export

`ProviderBackupCoordinator` reads one consistent database snapshot (see lettuce-database), derives the exact set of referenced secrets (provider credentials and every `AudioApiKey`) and loads only those from the native `SecretStore`, checking each generation before and after the read and rejecting rotating values. A value the store reports missing (a wiped keyring, a key sync could not deliver, a blank legacy key) keeps its reference, is listed as missing, and its account is returned in `ProviderBackupExport::missing_secrets`, so the restored account asks for its key again. The Hugging Face and CivitAI tokens are carried when set. Metadata and secrets are sealed as separate authenticated sections; secret plaintext lives in zeroizing buffers and never reaches metadata, errors or `Debug`.

`export_to` writes the backup into any writer one section at a time: data sections, then each media blob and conversation artifact read, checked and appended before the next is loaded, so memory is bounded by the largest single object. Media blobs are read through the confined media store in chunks and verified (size and BLAKE3) by the transfer layer; shared assets produce one media section, and missing ready content fails the export. Protected snapshot and replay payloads are streamed through `ConversationArtifactTransferPort` within the envelope's entry and byte budgets and must match their graph reference. Exported job and generation dispatch evidence is marked as overlapping audit evidence, never an additional charge. `export` is the in-memory wrapper.

### Restore

`BackupRestoreCoordinator` restores a version-2 backup as a replacement, never a merge:

1. Decode and stage the plan and build the restore admission request.
2. Install every media object into the shared content-addressed media root, each under its own `restore/<hash>.partial` so a concurrent sync download of the same blob is not truncated.
3. Move the backup's secrets to fresh references and store them (legacy import secret assignments inside the backup follow).
4. Open a new database file named by the restore id under `private-persistent-v2/databases` and write the graph through the restore writer.
5. Carry device-local state from the previously active file (`carry_device_local_state_from`).
6. Require the restored graph to read back equal to the decoded graph, with in-flight generation settled as interrupted exactly as the writer restores it, then record the admission.
7. Switch `AppDatabaseLocation` atomically to the new file. The previous file is never deleted, and secrets written by a failed attempt (including a failed pointer switch) are removed.

The Hugging Face and CivitAI tokens are written after the new database is active and only when the device has none, so a token entered on this device is never replaced; one whose status cannot be read or whose write fails is listed in `BackupRestoreReceipt::app_secret_failures`. Writes to the previous database after the device-local copy are not carried, so the host stops background work before a restore, and opens `AppDatabaseLocation::active_path()` with `AppBackend::open` on the next launch. Each restore stages into its own `<workspace>/<restore_id>` directory.

## Sync (`sync/`)

The sync design is described in the lettuce-sync README; this crate runs the session.

- Transport (`sync_transport`): the loopback or LAN transport binds a caller-selected socket, creates or accepts a six-digit session PIN and returns the sync transport traits only after both peers run SPAKE2 over the PIN (pairing protocol version 2) and confirm the key over fresh challenges. An observer learns nothing to test PIN guesses against, and an active attacker gets one guess per connection. A listener holds one freshly generated PIN and refuses every connection after three wrong proofs; sharing again binds a new listener. The sharing device's user approves each authenticated peer once its hello names it (`SyncPeerApprover`); a declined peer gets an explicit decline. A client that meets a 2.2.x host recognizes its handshake and reports the host's version with the same-version requirement; a 2.2.x client cannot read the current handshake, so both devices must be updated. The confirmation binds both connection roles and durable device identities; the ChaCha20-Poly1305 session uses direction-separated monotonic nonces. Frames are length-prefixed, capped at the payload limit plus 16 MiB before allocation, decoded with the same bound and rebuilt through domain validators. Host and client ordering keeps two large change frames from filling both socket buffers, and a bounded early-frame queue lets one peer serve media chunks while entering the next phase. Cancellation covers accept, connect and every read and write; a disconnect leaves the staged batch and confined media partials for the next session. There is no persistent peer trust or PIN storage.
- Hello (`SyncHelloCoordinator`): initializes the database-owned device identity before any change exists and builds the hello with a caller-owned fresh session id.
- Exchange (`SyncExchangeCoordinator`): negotiates the hello, runs the scan, exchanges frontiers, sends and stages or applies bounded batches both ways, records monotonic acknowledgements (which must name and causally cover the sent batch) and ends when both sides are quiescent. Unsupported input stays staged and returns a pending outcome without acknowledgement, so an upgraded retry resumes without data loss. Cancellation is checked at every transport await and before each storage boundary.
- Media (`SyncMediaCoordinator`): fetches the blobs of pending asset changes from the peer by content hash in chunks, resumable from the confined partial, then the staged batch replays and materializes without redispatch.
- Secrets (`SyncSecretCoordinator`): fetches values this device lacks or holds older, writes them under the generation seen when the phase began, versions local changes, and removes values nothing references.

Coordinator completion and errors are the backend status boundary; listener discovery and status events are frontend work.

## Jobs (`jobs/`)

- `job_recovery`: `recover_after_restart` (see Startup) and `StartupJobRecoveryCoordinator`, a bounded pass over expired claims that returns every recovered job with its policy action and snapshot, including kinds without a wired executor, so a host cannot silently consume unrelated work. Worker identity, resource admission, runtime inputs, polling and execution stay with the API's workers (`api::startup`).
- `one_shot_job`: a feature request that answers its caller directly (help me reply, scene prompts, design references) is admitted once per request id, claimed, run and settled as a job, so usage evidence and cancellation work like any feature request.
- `job_inference_usage`: every actual provider dispatch of a job (memory summary, tool requests, fallbacks and continuation, creation rounds, lorebook stages, Soul writer, speaker selection, chat) is recorded in the job usage ledger before the response is validated or checkpointed. Transport failures and cancellation stay distinct; round totals are not extra billable dispatches; a failure to store evidence, a cancelled primary response or a job cancellation during a tool-less response stops fallbacks, and an evidence failure is not classified as a provider failure. Other companion and staged callers keep their public provider-error mapping. The job store and the evidence repository must share durable job ownership. Completed replays add no dispatch.

## Usage (`usage/`)

- `UsageCostCoordinator::capture_job` (via `AppBackend::usage_costs`) captures an OpenRouter cost for a job dispatch: it reads the immutable response identity, resolves the same-revision enabled OpenRouter account, fetches generation metadata and the actual model's endpoint prices through the app-owned `OpenRouterBillingPort` (implemented by `RemoteProviders`), and writes an immutable cost basis. Replays return before any network or account lookup, and another writer's completed basis wins a race. Provider errors leave raw usage and cost state untouched for retry; a missing account, identity, usage, native totals or auxiliary counts, or ambiguous pricing, returns no cost.
- `AppActiveUsageTracker` counts only the time the window is focused, and `flush` adds it atomically to the device-local `app_usage_days` table (`lettuce_usage::AppUsageRepository`, one row per local day, never synced; backups carry the days and a restore merges the previous file's, keeping the larger time per day). The time is kept per local day, so a focused stretch crossing midnight is split between its days (where a clock change skips local midnight, the day starts at its first valid minute), a day whose write fails stays pending for the next flush, and concurrent flushes run one at a time so no time is written twice. `ApiContext::app_focus_changed` flushes when the window loses focus or the mobile app goes to the background, and `ApiWorkers::stop` on exit; a crash loses only the stretch in progress.

## Hard delete (`deletion/`)

`delete_conversation` and `delete_character` purge the rows (see lettuce-database) and then collect media; the API's `conversation_delete` stops what still runs first (see Application API). Every media call takes a `MediaGarbageScope`: the media store, the `AppDatabaseLocation` and the database file this process uses. Each run lists the other database files in the directory at that moment (one a restore kept or is writing), and an object any of them catalogs, in any state, is never deleted; when one cannot be read, the run deletes nothing and records a `media_collection_skipped` notice naming it.

`collect_media_garbage` runs queued sync-received deletes, lets the catalog release what nothing references and, holding the media store's ingestion lock, deletes those files only after that commit. Objects a backup export (from before it reads the catalog) or a restore (for the objects it installs) has pinned are left for a later sweep, and restore installs objects under the same lock. A file that cannot be deleted, or one a crash left between commit and deletion, is removed by `sweep_orphan_media_files`, which only looks at content-addressed files under the media root's `objects` tree and deletes those that neither this catalog (a blob in any state, so a `missing` blob can become ready again), another database file nor a backup pin names. That makes the sweep safe at startup. If media collection fails after a purge, the candidates stay queued.

## App version

`app_version(package_version)` appends `-cuda` for the CUDA build and nothing otherwise; the normal build is CPU with Vulkan. The suffix follows `lettuce-local-llm`'s `cuda` feature, which the `llama-cuda` feature enables.

Build features forward to the runtimes: `llama-vulkan`, `llama-cuda` and `llama-metal` to `lettuce-local-llm`, and `asr-vulkan`, `asr-cuda`, `asr-metal` and `asr-rocm` to `lettuce-speech`. None is on by default; the Tauri shell combines them into its product builds. The update check itself is in the frontend.

Embedding sessions are retained across calls only when device `embedding.keep_model_loaded` is enabled. With it off, each token-count or embedding call owns its session until the call returns; workflow wrappers retain only source metadata and refuse a model-space change during a use. Embedding and Thymos installs share a sequential install lane. Audio provider verification can use an unsaved configuration and a borrowed credential without writing either. Providers with no remote voice listing return their built-in catalog or an empty list.

The speech commands accept file sources, ingest audio into the media store, and return jobs or asset references. Dictation writes a WAV spool in app scratch space; stop ingests it and atomically admits its transcription, cancel discards it, and startup removes abandoned scratch recordings. Job admission receipts freeze transcription and synthesis inputs before the worker starts, so a replay survives source or provider deletion. Desktop capture is a shell port; the application itself remains independent of Tauri.

The optional-model API exposes embedding inventory, selection, install, removal, raw-cosine comparison and unload, plus Thymos status, install and removal. Embedding installs store their resolved pin for queued recovery and finish with the versioned legacy health probes. Only an install requested with `enable_dynamic_memory` activates the legacy dynamic-memory defaults after a passing health check. Removal is refused while an embedding install is queued or running. These models use the legacy app folders (`models/embedding` and `models/thymos`), which are siblings of the default GGUF root (`models/gguf`); a custom GGUF root can overlap them.

Retained Whisper, Kokoro, embedding and Thymos locations are device-local settings. Their defaults remain the app folders. A custom GGUF root that contains them moves those roots too: copied embedding and Thymos manifests verify rebased artifact paths, Whisper paths commit with the device setting and model profiles, and Kokoro descriptors remain relative to their root. Move admission checks active local speech and loaded optional models; queued local speech waits behind an overlapping move.

The speech library API lists, updates and removes audio provider and user voice metadata without exposing credentials. ASR vocabulary, corrections, ignored suggestions and voice examples can be listed or removed, correction suggestions are read-only, and filtered learning exports use a host FileTarget. Voice examples carry asset references.

Audio credential status exposes availability and generation. Existing credentials rotate with a generation check; a stale writer gets Conflict. Credential values remain in the device secret store.

Voice search delegates ElevenLabs queries to the existing provider control adapter without caching the results. Voice-design previews execute inline with shutdown cancellation and a temporary media asset for each result; the API returns the generated voice identifier, duration and asset URL.

Message playback resolves the selected visible message and the character's current voice, removes hidden thoughts and scene instructions, and substitutes the current display names. Admission freezes that narration and voice.
