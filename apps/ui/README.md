# LettuceAI UI

The React frontend the Tauri shell (`apps/tauri`) loads. It is built with Vite, React 19 and TypeScript in strict mode, styled with Tailwind CSS v4 and the `@lettuceai/crisp` component library, and managed with bun. [PLAN.md](PLAN.md) describes the target product structure; this file describes what is built.

## Layers

`src/app/` composes the application: `bootstrap/` creates the runtime (API client, query client, i18n instance, router) and renders it, `providers/` holds the provider stack, `router/` builds the code-based route tree, `shell/` holds the root layout and the placeholder status screen, and `error-boundaries/` holds the fatal boundary and the default route error and not-found states.

`src/api/` is the only code that knows how the backend is reached. `generated/bindings.ts` is written by tauri-specta from the Rust command signatures and is never edited by hand. `transport.ts`, `tauri-transport.ts`, `mock-transport.ts`, `client.ts` and `query-keys.ts` wrap it, as described below.

`src/features/` will hold one folder per product feature, each exposing a small public `index.ts` that exports its page components. `src/entities/` will hold domain building blocks several features render. `src/shared/` holds code with no feature knowledge: `ui/` (shared components such as the typed failure state), `i18n/`, `hooks/`, `formatting/` and `testing/`. `src/styles/` holds the global stylesheet.

## Backend access

A `Transport` has three operations, all typed from the generated bindings: `call` runs a command and resolves to its `{ status: "ok", data }` or `{ status: "error", error }` outcome, `stream` runs a command that takes a channel and passes each event to a callback, and `subscribe` listens to the application-wide `AppEvent`. Command names, request arguments, stream events and results are derived from the generated `commands` type, so a new backend command is available through the transport as soon as the bindings are regenerated. Any command with a channel parameter is a stream command, and callers pass its other arguments without the channel; a type assertion in `tauri-transport.ts` fails the build if a command ever takes its channel anywhere but last.

A stream's events are independent of its call promise: they may arrive before or after the promise settles, and the terminal event (completed, failed, cancelled) is in the stream, not in the promise. The handler stays attached until the caller aborts the `AbortSignal` it passed, which it does on unmount or after the terminal event; the Tauri transport then drops the channel's handler, and a server transport would close its subscription. A signal that is already aborted cancels the stream with a `cancelled` failure before the command is sent, and a call that fails detaches its handler at once because no events follow; after a successful call the abort listener stays, since that is how late events are detached.

`tauri-transport.ts` forwards application calls to the generated `commands`, wraps stream callbacks in a Tauri `Channel`, and listens to `events.appEvent`. `window-controls.ts` separately adapts the current desktop window's controls and resize events; it loads Tauri only inside a desktop shell. `mock-transport.ts` is an in-memory implementation with per-command handlers, used by tests and by the browser development mode. A later HTTP or WebSocket transport for a server mode implements the same interface. Native imports remain inside `src/api/`.

`client.ts` wraps a transport in the `ApiClient` the UI uses. An ok outcome resolves to its data. An error outcome that `isApiError` recognizes (an object whose `code` is one of the generated `ApiErrorCode` values, with a message and nullable details) rejects with an `ApiFailure` carrying that code and details. Anything else, whether the transport threw or Tauri rejected with its own string (an unknown command, a denied permission, arguments that did not deserialize), rejects with an `ApiFailure` whose code is `transport` and whose `cause` is the original value. The backend's `message` is diagnostic text for logs; the UI shows localized copy chosen by `code`.

`selectTransport` picks the Tauri transport when `window.__TAURI_INTERNALS__` exists. Without it, a development build falls back to the mock so the UI runs in a plain browser, and a production build fails with a `transport` failure that the bootstrap renders as the fatal screen, so a missing backend is never hidden behind fake data. The mock branch is guarded by `import.meta.env.DEV`, a build-time constant, so production bundles do not contain the mock at all; the Tauri transport is loaded with a dynamic import, so a browser development session never loads Tauri code.

Media is never passed as bytes: every `AssetRef` from the backend carries the `url` the UI loads as is, and uploads pass a `FileSource` path or URI that Rust reads.

## State

Server state lives in the TanStack Query cache under keys from `query-keys.ts`. Cached data never goes stale on its own (`staleTime: Infinity`), and the query client does not retry failures or refetch on window focus or reconnect: data changes when a mutation or a backend event says so, and a failure is shown with its typed code instead of being retried blindly. `AppEventBridge` subscribes once to the application event stream when the providers mount and invalidates the query keys that `appEventInvalidations` in `query-keys.ts` maps each event type to; an event type missing from the table invalidates nothing. Once the subscription is live the bridge invalidates every query once, so an event that fired while the page was starting is not lost.

Keys nest so that invalidating a prefix refreshes everything under it: `conversations.messages(id)` sits under `conversations.detail(id)`, so the `generation_settled` rule refreshes a conversation's message queries along with its view. `app.status` has no event that refreshes it; the placeholder only shows the version and platform, which cannot change while the app runs. Any other `AppStatus` field (the UI state, legacy detection, conflict and purge-notice counts) must get its own query keyed to the backend event that changes it before a screen uses it. Route and workflow state belongs in typed route params and search params, and ephemeral UI state stays in components.

Conversation generation reports model loading and image-prompt preparation through one Crisp progress toast, updated in place at the top of the screen. The toast follows store events independently of timeline visibility and is dismissed when preparation ends or the view unmounts. Streaming messages omit empty preparation bubbles and pause their cursor while an image directive is open, then resume it for visible text after the directive closes.

The router is TanStack Router with a code-based route tree. Its context carries the `ApiClient` and the `QueryClient`, so route components and loaders get the client from the router instead of from a global. Route components are imported directly: the app ships as one local bundle, so splitting routes into lazy chunks would only add a loading state to every navigation. Features export their page components from their `index.ts`, and the pending screen shows only while the first app status loads. Crisp's `AppShell` uses a rail on desktop and four tabs on mobile or narrow windows. Tabs appear only on Chats, Groups, Discover and Library; Settings is the rightmost action in those pages' mobile title rows. Desktop keeps its Settings footer and defaults to showing the sidebar on detail pages; Home's View menu can disable that through the device's `sidebarOnDetailPages` UI preference. Settings uses an index and back controls when navigation is hidden. Chats shows characters and recent chats. `/characters/new` creates a character by hand in four steps (identity, starting scenes, details, extras), reached from the Create sheet, the empty Chats screen and Library character-create actions. Scenes update the selected list entry live; compact layouts push its editor within the page and Back returns to the list. Empty scenes are optional and are omitted from the final save. Settings exposes About, Providers and Models; Groups and Discover currently render their page titles. Library ports design-lab’s LibraryScreen with six searchable filters, poster cards, image tiles, audio rows, typed cursor-backed data and bottom action menus. Entry and audio feeds load at most 24 items per page, and image feeds load 32, as the end enters view, and media loads only for its selected filter. Search is debounced and runs in Rust; card, image and audio rows use Crisp VirtualList in the page scroller, with two overscan rows. Every filter shows its full count through the lightweight library_counts aggregate query, independently of the loaded pages or active filter. The desktop sidebar reuses cached character identities without fetching the entire home catalog. Its small editors create and update names/descriptions while preserving hidden entity fields and revision fences. Native file pickers handle import/export and media saving; in-use media cannot be removed. Lorebooks expose name editing and their real entry count in the menu; the backend has no lorebook description or summary count field. The full character/persona/lorebook editors remain separate work. Onboarding flows hide navigation and retain the desktop title bar. Window controls support minimize, toggle maximize, close and edge resizing. Resize events update the frame's rounded corners without polling; fullscreen and maximized windows use square corners.

## Startup

`main.tsx` calls `bootstrap`, which creates the i18n instance, selects the transport and renders the app. If the backend cannot be reached it renders the localized fatal screen instead. If localization itself fails, or anything else rejects before React renders, it writes a plain-text message into the page, the only English text that does not come from a locale file.

## Localization

All user-facing text goes through i18next and react-i18next. Each namespace is a JSON file under `src/shared/i18n/locales/<language>/`; `common` is the only one so far, and each feature adds its own. The resources are registered in `src/shared/i18n/index.ts` and typed through `i18next.d.ts`, so a missing key is a type error. Error codes map to copy under `errors.code`. Tests render the app in i18next's `cimode`, where `t()` returns the key, to prove a screen has no hardcoded strings, and the `react/jsx-no-literals` lint rule rejects literal text in JSX children and in text props such as `title`, `label`, `placeholder` and `aria-label`, while class names, data attributes and the `{" "}` spacing idiom stay free. The restricted props cover every text-bearing prop in crisp's component types; the `cimode` test remains the backstop for anything the list misses.

## Theme

`ThemeProvider` from crisp applies the theme variables and remembers the chosen preset, `MotionConfig` honours the reduced-motion preference, and `src/styles/index.css` imports Tailwind, the bundled Inter font and crisp's stylesheet and points Tailwind's source scanning at crisp's build. The font is bundled rather than loaded from a CDN because the shell's content security policy allows fonts and styles only from the app.

## Boundaries

oxlint enforces the import rules: `@tauri-apps/*` may only be imported inside `src/api/`; outside `src/api/` the generated bindings may only be imported for types and the transports not at all (tests may use the mock); a feature is imported only through `@/features/<name>`; and `shared/` and `entities/` may not import a feature, which also holds for their tests. `__TAURI_INTERNALS__` may not be read outside `src/api/`, as a global or as a property. The tests in `test/lint-boundaries.test.ts` run oxlint on the fixtures in `test/lint-fixtures/` to prove each rule fires, and `test/architecture.test.ts` applies the same rules to relative import paths, which a lint pattern cannot judge, and rejects any mention of `__TAURI_INTERNALS__` outside `src/api/`, including the string form of an `in` check.

## Running

`bun install` installs the dependencies. `cargo tauri dev` in `apps/tauri` starts `bun run dev` here and opens the app on the Vite server at port 1420; `cargo tauri build` runs `bun run build` and bundles `dist/`. On a mobile device the Tauri CLI sets `TAURI_DEV_HOST`, and the dev server then listens on that host with hot reload on port 1421.

`bun run dev` alone serves the UI in a plain browser at `http://localhost:1420` with the mock transport. Bun 1.4.3 or newer is required. `bun run typecheck` uses Bun's built-in type checker through `bun --check`, which follows both projects referenced by `tsconfig.json`. The explicit flag bypasses this package's `check` script. `bun run check` runs the type check, the linter and the tests; `bun run build` runs the same type check and writes the production bundle to `dist/`. TypeScript remains installed for editor tooling. The build targets ES2023, which every webview Tauri 2 runs on (WebView2 on Windows, WKWebView on macOS and iOS, WebKitGTK on Linux, the system WebView on Android) supports.

`index.html` must not contain an inline `<style>` or script, because the shell's content security policy would then drop `'unsafe-inline'` and break React style attributes.

Provider control errors include `in_use` for referenced records and `malformed` for unreadable provider responses. The API client preserves these typed errors and shared failure screens render their localized copy.

Generated provider contracts expose stored-certificate validity with an InvalidPem reason, CertificateAlreadyImported details with the existing id, and optional redacted verification messages with MissingApiKey or InvalidApiKey reasons.

Startup reads the install's locale from device UI state. When no locale is stored, it imports a readable legacy app-locale webview key, then detects the first supported browser language, otherwise uses English. Subsequent startup uses device state. Persisting the initial device choice is best-effort, so a storage failure still allows startup.

SettingsChanged invalidates settings queries, and ContentFilterHit invalidates the filter-log key. No filter-log polling interval is installed. Locale import accepts the legacy supported locale identifiers and detects a browser language when a stored key is invalid.

### Provider and model settings

Providers and Models port the layouts from design-lab's `SettingsScreen.tsx`. The provider tabs use the language and audio provider APIs; blank keys preserve existing credentials. Model rows support editing, provider grouping, default selection, duplication, UEC export through the native save picker, and confirmed deletion. Editors preserve configuration they do not expose and submit revision fences. Model configuration defaults are shared with onboarding through `entities/model`.

The model editor at `/settings/models/new` and `/settings/models/$modelId` ports `ModelFlows.tsx` from design-lab. Desktop uses a section sidebar; compact layouts open sections as sub-views. Both pin the save bar over the scrolling content with the demo's transparent background and 8 px backdrop blur. It appears for new models or unsaved changes and animates out when edits are reverted, discarded or saved. Model config stays in the Rust `ModelProfileConfig` encoding, including tagged per-feature overrides and unknown fields. Unset values show `sampler_defaults` or the runtime value where known. Local sampler defaults follow `lettuce-local-llm/src/sampler_profile.rs`, `sampler.rs` and `request.rs`; the cloud token fallback follows `lettuce-providers/src/common.rs`. Image profile defaults come from `hfImageBundleProfiles`. Server-owned values without a published default keep a provider-default placeholder. The editor uses the shared onboarding model picker and custom menus, with the design-lab section transition. Device placement, context recommendations, OpenRouter endpoints and image component detection use their existing API commands. The context API exposes per-memory-pool model, KV and working-memory estimates for the selected context, batch, flash-attention and sliding-window settings. The editor renders the demo's segmented fit panel using those byte counts; existing allocations are retained in the capacity/free calculation. Context edits keep the current panel visible while a 120 ms debounce coalesces new estimates. Preview planning uses cached model metadata and the existing reserve formulas without allocating GPU compute buffers. Deletion from either the list or editor fetches `modelUsage` before showing the affected characters, groups and roles in the confirmation.

The three model shortcuts open sheets for Hugging Face GGUF downloads, global context/KV defaults, and the image LoRA library. Downloads register model profiles and follow backend job events, including active downloads when reopening the sheet. CPU threads and GPU layers are per-model fields. Provider/model/settings mutations invalidate their query caches; no polling is added.

Image generation settings expose avatar and scene switches, their model choices, scene mode and the prompt writer. Settings writes use the same serialized, revision-fenced path as Memory and retain the page and scroll position. Local image management follows the design-lab Engine, Image models, Hugging Face bundle and LoRA pages: engine builds, per-build GPU policy, upscaler installation, catalog variants, fit checks, registration repair and model removal. The shared LoRA library adds trigger-word editing/discovery and CivitAI browsing. Downloads use job events; leaving a page detaches its watcher without cancelling the work. Android and iOS retain remote image settings and hide local engine management.

Reply helper is a direct Settings destination alongside Smart creator, replacing the Advanced placeholder. It follows design-lab's ReplyHelperDesign, uses real text models and prompts filtered by style, and saves through the existing serialized settings writer. Numeric drafts survive failed writes and commit after a pause, blur or Enter. Model and prompt pickers retain the page and scroll position; Manage prompts links to the System prompts page. Smart creator's screen remains pending.

System prompts follow the design-lab list, editor and entry drawer. Grouped and flat lists expose all editable prompt kinds, copies, native import/export, app default selection and built-in reset. Entry order, placement, conditions and image slots use the typed prompt API; placeholder requirements are validated in Rust. Preview renders the unsaved draft without storing it, with selected characters/personas and the backend's sample context. Unsaved changes and list navigation are retained across editor actions.

`entities/provider` exports `ProviderSelect`, the provider counterpart of Crisp's `ModelSelect`: logo and group options in a desktop menu, with a bottom sheet on mobile. Provider type and model-account selection use it. Settings pages remain statically imported. The custom OpenAI/Anthropic editor exposes endpoints, authentication, model-response paths, role mapping, streaming support, tool choice, message merging, reasoning template arguments and TLS exceptions using the current `ProviderConfig::Custom` shape.

The full editor comparison also covers GPU groups and conditional device selection, endpoint routing modes, LoRA strength sliders, template placement, component profiles, scope hints and compact sub-view actions. Separate key/value cache types remain by request and inherit atomically, as in `llama_resolution.rs`. VRAM limits display GiB and save bytes. Sequence fields use escaped comma-separated text without changing their stored arrays. Sampler stages use a vertical pointer-driven reorder list with keyboard and arrow controls, explicit removal and re-adding; an empty chain stays an explicit empty array. Template viewing and editing use a highlighted drawer that fills the available height. Apply stages template edits in the model draft; Cancel leaves it unchanged and Save persists it. Runtime defaults take precedence over illustrative demo values (including SWA, sampler order, speculative decoding and image tiling). The nine Rust feature targets, pinned save bar and onboarding picker remain intentional differences. Image/server defaults not exposed by the existing APIs remain automatic instead of displaying invented numbers; a global OpenRouter pin cannot be cleared through a model-only override.

The memory card separates the model estimate from memory already in use and labels every bar segment, with decimal GB throughout. Chat context also shows the resolved KV cache type. Separate K/V controls appear only after choosing Custom; switching back to a shared type removes the split pair. Recommendations explicitly reserve a safety margin.

Library cards and image tiles use the API-provided preview URL when present. Opening image details and exporting still use the original asset, and older cached records without previews retain their original URLs.

Image pages request 32 items, matching the 8 by 4 desktop loading grid. Entry and audio pages retain 24 items. Grid requests explicitly omit usage references; an image action sheet loads those through mediaReferences only when opened, with pending, error and retry states.
